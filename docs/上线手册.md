## 2. 上线七步

1. **预检**:§1 全 14 行复核 + 双人签字;CI(main)全绿。
2. **翻转**:`.env` 按 §1 逐项落地;`docker compose config` 通过。(注:OPT-25 后
   env 里的大模型 `*_API_KEY` 已**不参与解析**,可从 .env 移除;模型 Key 改走管理端
   录入、加密进库。`APP_MASTER_KEY` 反而成为**必配**——它是库内供应商密钥的加密主密钥。)
3. **迁移**:**先 `deploy/backup.sh` 自动备份** → `docker compose up -d`(migrate 一次性服务) → `curl http://localhost/system/info` 确认 `migration_dirty=false` 且 `migration_version` 为目标号。
3a. **配置模型(OPT-25 新增硬前置,不做则上传/问答全线 503)**:
   - superuser 引导(无自助接口,刻意最小暴露面):`docker compose exec -T postgres psql -U postgres -d wenqu -c "UPDATE users SET is_superuser=true WHERE username='<运维账号>';"`;
   - 按 `docs/api/m4-模型管理-接口说明.md` §6 调 `POST /api/v1/admin/model-providers|models`:至少一个默认 chat + 一个默认 embedding(**dims 必须 1024**,与向量列硬约束一致);密钥只在此入口出现明文,落库即 AES-GCM 加密;
   - 复核:`GET /api/v1/models` 的 `defaults` 含 chat 与 embedding。
3b. **prod 每空间必须自配向量化 Key(OPT-27 硬约束,不做则该空间上传入库/检索 503)**:
   - 全局 embedding 兜底**只在 `APP_ENV=dev` 生效**,prod 一律不回落(用户裁决 2026-09-20);
     全局层模型对空间仍然可用(chat 默认"空间→全局"解析),**只有 embedding 必须空间自有**;
   - 由该空间 Admin 在配置页(或 `PUT /api/v1/spaces/{sid}/model-config/embedding-key`)填入
     百炼账号的 Key;对话/重排模型同页自配,门槛同为 Admin+;
   - 上线日抽查未配 Key 的空间:`docker compose exec -T postgres psql -U postgres -d wenqu -c
     "SELECT s.name, COALESCE(m.embedding_key_encrypted<>'' , false) AS has_key FROM spaces s
      LEFT JOIN space_model_settings m ON m.space_id = s.id ORDER BY has_key;"`;
   - 同轮安全口径:空间自配的 `base_url` 在 prod 过 SSRF 闸门(内网/回环/元数据地址 422)。
     确需内网自建网关的部署,运维显式配 `APP_ALLOW_PRIVATE_MODEL_URLS=1` 并在翻转项 #4 备注。
4. **冒烟**:§3 七条全过。
5. **观测**:人为制造一次死信(上传损坏文件)→ 确认状态"失败"+ error_message 可见 + 可重解析;`docker compose logs worker` 有告警级日志。
6. **交付**:本手册 + `deploy/backup.sh|restore.sh` 交运维;回滚预案 = §6。
7. **48h 复盘**:错误率/慢查询/续流回收异常回看,结论进 V1 交付台账。

## 3. 冒烟七条(逐条取证)

执行工具:`server/scripts/go_live_smoke.py`(在演练栈 server 容器内跑,打生产唯一入口
`http://web:8080`,真 gRPC parser / 真 worker / 真模型;条 7 由手册外的 compose 命令补)。
`docker compose exec server python scripts/go_live_smoke.py`。
OPT-25 适配:脚本开头有"前置"检查(库内 chat+embedding 默认模型可用,即七步 3a);
库空时会尝试自助配模型,需容器环境提供 `WENQU_ADMIN_TOKEN`(superuser JWT)+
`DASHSCOPE_API_KEY` + `DEEPSEEK_API_KEY`(仅冒烟用,配的是 smoke-* 前缀供应商);
不满足即整轮判失败退出。OPT-26 适配:条 5 建 Key 必须带 `member_user_id`,
条 6 新增"Viewer 建 Key 403"检查(共 25 项;上线日按新基线复跑)。

| 条 | 动作 | 预期 |
|----|------|------|
| 1 | PDF/Office(docx)/Markdown/表格(xlsx) 各传一篇 | 全部 `pending→completed`,分块/向量化正常 |
| 2 | 传损坏 docx | 状态"失败",任务 `error_message` 可见,reparse 可重试 |
| 3 | 提问带引用;删除知识库再问 | 答案带角标引用;**兜底话术而非报错** |
| 4 | 流式中途断网重连 | 续流按 `seq` 补播,不重不丢(OPT-3) |
| 5 | 建 KB 范围受限 API Key(OPT-26:绑定成员,Admin+ 签发) | 范围内可用;范围外 403 `API_KEY_SCOPE_DENIED`;能力外/未登记路由 403 `API_KEY_CAPABILITY_DENIED`;**未接 Key 认证的路由对 Key 是 401(与"没登录"同构,同为拒绝)**;审计有记录 |
| 6 | Viewer 调管理接口;Viewer 尝试建 Key | 均 403 `FORBIDDEN`(非成员路径 404 防枚举)+ 审计 `access.denied` 有记录 |
| 7 | `docker compose restart server` | 任务自动恢复(租约重认领),无任务卡 running(注:tasks 表执行态枚举是 `running` 而非 `processing`;核查 SQL 用 `status='running'`)+ `/health` 通过 |

- **演练实测**(2026-09-20,prod compose + 真模型,经 nginx 入口):**23/23 全绿,零重试**。
  条 7 补充取证:restart 后 `/health` 在 nginx resolver TTL(≈10s)内瞬时 502、随后 200;
  死 worker 租约用"置 `running`+`claimed_at` 早于 timeout"模拟,worker 30s 回收周期打出
  `recovered 1 stale tasks` 后任务重跑至 `succeeded`,终态 `status='running'` 计数 0。
- 翻转项 #7 复核口径修正:`/docs`、`/openapi.json` 要在 **server 源站**验 404;
  经 web 入口访问该路径返回的是 SPA `index.html`(nginx history 回退),不是 API 文档。

## 4. 备份恢复(实测记录)

- **备份**:`BACKUP_DIR=<路径> deploy/backup.sh` → `pg/<db>.dump`(-Fc,索引定义随 schema)+ `minio/` 整桶 + `manifest.txt`(alembic 版本/表数/对象清单)。
- **恢复**:`deploy/restore.sh backups/<TS>` → 停写 → DROP/CREATE → pg_restore → mc mirror --remove → 核对 manifest → 探活;末行打印总耗时。
- **演练结论**(2026-09-20,本机 dev 数据 + prod compose 实起):

| 阶段 | 耗时 | 结果 |
|------|------|------|
| 备份(backup.sh) | **3s** | pg dump + minio 2 对象 + manifest 齐 |
| 清空(DROP/CREATE DATABASE + 桶对象删除) | ~10s | 库表/对象全零 |
| 恢复(restore.sh) | **13s** | alembic=0011、行数与恢复前逐项一致(users 3 / spaces 2 / kb 2 / docs 2 / chunks 4 / messages 4),向量索引存在 |
| 恢复后冒烟 | — | 容器内 `e2e_smoke` 21/21 + `go_live_smoke` 23/23(真模型,经 nginx) |

- 备份→恢复→冒烟全程 < 1 分钟,**RTO 4h 余量极大**;演练数据量 ≪ 生产,生产首次备份后需按线性外推登记。
- Windows/Git Bash 执行注意(已在脚本内处理,操作仍需知):`restore.sh` 的 `docker compose cp` 需
  `MSYS_NO_PATHCONV=1` 前缀运行(否则 `/tmp/...` 被改写);`docker compose` 的容器路径参数用服务名(`server:`)而非容器名。
- 演练隔离方式:`COMPOSE_PROJECT_NAME=wenqu-drill` + 独立卷 + 独立宿主端口(`WEB_HTTP_PORT=18080`),
  **绝不**对 dev 栈执行 restore(DROP DATABASE)。

## 5.1 演练发现的缺陷(本轮已全部修复并有测试/复跑证据)

| 缺陷 | 发现渠道 | 修正 |
|------|---------|------|
| "创建后立即发起的下一个请求"偶发 401/404(注册→建空间、建库→上传、建 Key→检索) | Go-Live 冒烟脚本 ok_req 重试日志抓到原始响应 | 根因:FastAPI yield 依赖收尾 commit 晚于响应发出,`get_db` 把 commit 放收尾 → 真实 HTTP 下写后立读不可见(进程内 TestClient 测不出)。新增 `api/routing.py CommitBeforeSendRoute`:端点返回后、响应发送前提交;全部 DB 路由挂 `route_class=`。时序单测 + 冒烟复跑零重试为证 |
| `storage.delete_prefix` 传裸字符串给 `remove_objects`,删知识库 500 | 冒烟条 3 | 改传 `DeleteObject`,契约单测同步钉住 |
| gRPC 拒绝裸 `:50051` 监听地址,parser 崩溃循环 | prod 起服实测 | 默认与 compose 改 `0.0.0.0:50051` |
| server 镜像构建即失败(uv 找不到 pyproject) | build | Dockerfile `WORKDIR /repo/server` |
| `server/.env` 被烘进镜像,prod fail-closed 门禁在容器内失效 | 门禁实测"该拒不拒" | `.dockerignore` 扩为 `**/.env*`(根 + web + parser 各补一份);历史本地镜像含密钥副本,**上线日一律以重建镜像 + digest 为准,旧镜像不得推送** |
| nginx 静态 `proxy_pass` 只在加载配置时解析上游 DNS,重启 server 后 502 | restart 实测 | `resolver 127.0.0.11` + 变量式 `proxy_pass`(运行时重解析);restart 后 TTL(≈10s)内 502 属预期,已写进条 7 口径 |
| 备份/恢复脚本用 minio 镜像内未授权的 `local` 别名 | 演练实测 | 显式 `mc alias set bkw`;DROP/CREATE 拆两条 psql(-c 隐式事务) |
| 冒烟脚本误用 `Authorization: Bearer sk-live-…` | 条 5 全 401 | 按契约改 `X-API-Key` 头 |

## 6. 回滚预案

- 应用层:`WEB_/SERVER_` 镜像 tag 回退到上一固定版本 `docker compose up -d`(无 schema 变更时零成本);
- 含迁移的发布:回滚 = `deploy/restore.sh <本次上线前自动备份>`(整库+对象存储同点位),**迁移后备份未成功前禁止继续发布**;
- 回滚后必查:`/system/info` 的 `migration_version` 与镜像内 alembic head 一致、`migration_dirty=false`。

## 7. 自动化发布(CD)

发布路径:GitHub → Actions → **Deploy-prod → Run workflow** → 填 `version`(如 `v1.2.0`)与
`confirm`(原样再打一遍 `deploy v1.2.0`) → 发布前校验 → 三条门禁(server/parser/web,与 CI 同一套) →
生产机 runner 上跑 `deploy/deploy.sh v1.2.0`(= 本手册 §2 步骤 3 的自动化:水位 → 构建 → 卷前缀 →
迁移前强制备份 → compose up → `/system/info` 校验 → **之后**才推 ACR 归档并打回收清单)。

**为什么是手动点而不是"打 tag 自动发 + 审批门"**:Environment 的 required reviewers 在 GitHub Free 上
**只对公开仓库开放**,私有仓库调用返回 422(billing plan 不支持)。本仓库为保护生产机 runner 已转私有,
故把"人墙"改成 Run workflow + 复述版本号。代价是少了一道平台侧审批记录,收益是误发门槛更高
(必须亲手把版本号再打一遍)。Environment 仍在,只是只承担 secrets 投喂,不承担审批。

`preflight` 另有一条硬规则:**tag 必须指向 main 的最新提交**,否则拒发——门禁跑的是 main HEAD,
部署的就必须是同一份代码,不然"CI 绿了"和"发出去了"验的不是同一个东西。

`deploy/deploy.sh` 的四道硬门,任一不过即中止:

| 门 | 拦的是什么 | 失败表现 |
|----|-----------|---------|
| 磁盘水位 | 门 2 的备份要写到同一块盘;写到一半盘满 = 迁移前保险是残缺的 | 阈值 = `max(WENQU_MIN_FREE_GB, 上次备份×2)`;不足则自动清构建缓存复检,仍不足即**拒发并打印回收清单** |
| 项目名确认 | compose 项目名决定数据卷前缀,猜错等于对**空库**发布 | 探到多个/零个候选即拒发,需 `WENQU_COMPOSE_PROJECT` 显式指定 |
| 迁移前备份 | schema 前移不可回退 | `backup.sh` 不成功就不进 `compose up` |
| 健康校验 | 起服≠可用 | `migration_dirty≠false` 或 `/system/info` 无响应 → 应用镜像回滚到上一 tag |

回滚只回**应用镜像**;数据库回库是破坏性操作,脚本只打印可照抄的 `restore.sh` 命令,不代跑。

顺序上有一条刻意的取舍:**归档推 ACR 排在三道门之后**(构建 → 门 1/2 → 起服 → 门 3 → 推送 → 回收清单)。
广州机往杭州 ACR 公网上传是分钟级到十几分钟级,放在起服前等于让档案馆拖住发布;放在后面则慢与失败都只影响
"ACR 有没有这一份",不影响线上。推送结果逐条记进 `~/wenqu/.deploy-state.archives`,供 §8 判断某版能否安全删。

一次性环境准备(换机/重建时照此重做):

1. 生产机注册 runner:GitHub → Settings → Actions → Runners → New self-hosted runner,
   标签 `prod,wenqu-deploy`,装在 `~/actions-runner`(勿放进 `~/wenqu`,会污染 git 工作区);
   服务化:`sudo ./svc.sh install ubuntu && sudo ./svc.sh start`。
2. GitHub Environment 名为 `production`(一字不差),该环境 Secrets 只放
   `ACR_USERNAME` / `ACR_PASSWORD` 两项(**业务密钥一概不进 GitHub**,见下);
   命名空间 `wen_qu` 明文写在 `deploy-prod.yml`,**不要收进 Secrets**——Actions 会把日志里任何等于
   secret 值的文本替换成 `***`,回收清单打印的 `docker rmi` 会因此变成跑不通的命令。
   审批规则在 Free 私有仓库不可用,不必也无法配。
3. 生产机 `~/wenqu/.env` 持有全部业务密钥;`deploy-prod.yml` 只以绝对路径引用它。
4. ACR 个人版私有命名空间,镜像归档为 `<ACR 实例域名>/<ns>/wenqu-{server,parser,web}:<tag>`;
   日常部署用本机构建产物,ACR 是归档与跨机恢复位。
   **域名必须用控制台"访问凭证"页给出的实例专属域名**
   (`crpi-xxxx.<地域>.personal.cr.aliyuncs.com`),老的共享域名 `registry.<地域>.aliyuncs.com`
   拿同一套凭据会返回 401;该域名写在 `deploy-prod.yml` 的 `ACR_HOST`,登录与打 tag 共用它。
   命名空间还需开启"自动创建仓库",或预先手建 `wenqu-server`/`wenqu-parser`/`wenqu-web` 三个私有仓库。
   **构建必须关掉 provenance attestation**(buildx 默认会给镜像附一份"构建来源证明",把镜像导出成 manifest
   索引;个人版 ACR 不认索引里 `application/vnd.oci.empty.v1+json` 这个 class,报 `unknown manifest class`,
   表现为**层全部 Pushed、最后提交 manifest 才失败**,实测白传 8m46s 且 ACR 上一份都没存下)。
   已由 `deploy/deploy.sh` 顶部 `export BUILDX_NO_DEFAULT_ATTESTATIONS=1` 固定,人工在本机 build 也要带上它。

未纳入 CD 的(刻意保持人工):§2 的 3a/3b 模型配置、§1 翻转项复核、§3 冒烟七条取证、§4 定期备份演练。

**红线**:生产机这台 runner 带 `prod,wenqu-deploy` 标签,**任何 `pull_request` 触发的 job 一律禁止 `runs-on: self-hosted`**——
否则一条被批准的 PR 就会在生产机上执行代码,而该机器可读 `~/wenqu/.env`(DB/MinIO/JWT 全套口令)。
发布链只允许由 `workflow_dispatch` 手动触发(且要求复述版本号),不接受任何 push/PR 自动落到生产。

## 8. 磁盘回收(发布次数增长带来的唯一长期风险)

发布链路本身不堆容器也不涨内存(`compose up -d` 原地替换旧容器;日志已按 `LOG_MAX_SIZE`×`LOG_MAX_FILE` 封顶),
会涨的是**磁盘**。`deploy/cleanup-report.sh` 把"该删哪些"算成一条可直接复制的命令,**严格只读**:
删除一律由人执行 —— 省的是可再生的空间,赌的是不可再生的回滚保险与备份,不对等。

**唯一的例外是构建缓存**:它是 100% 可再生的(删了只让下次构建变慢,不丢任何数据),所以门 0 在水位不足时
会自动 `docker builder prune` —— 先清 7 天未用的,仍不足再清空全部。**镜像 tag 与备份目录永不代删。**

```bash
bash deploy/cleanup-report.sh          # 磁盘现状 + 旧镜像清单 + 过期备份清单
bash deploy/cleanup-report.sh images   # 只看镜像(备份那类用 backups)
```

每次发布成功时 `deploy.sh` 会在归档推送之后自动打一遍这份清单;脚本自身报错也只告警,不影响发布结论。

**从 Actions 日志复制命令时留意 `***`**:日志里任何等于某条 secret 值的文本都会被 GitHub 替换成 `***`,
镜像名/路径正好命中就成了一条废命令(踩过一次:命名空间被配成 secret 导致 `docker rmi` 报
`invalid reference format`)。遇到这种清单,改在生产机上直接 `bash deploy/cleanup-report.sh` 重拿一份。

### 8.1 旧镜像 tag

脚本保留三类,其余列成一条 `docker rmi`:①`docker ps` 里真在用的;②版本号最高的两版(当前 + 上一版 =
自动回滚的目标);③`latest`(人工 `compose up` 不带 CD 变量时的兜底)。只匹配 `<前缀>/wenqu-{server,parser,web}`,
postgres/minio 等第三方镜像绝不进清单。每个候选还带一列归档状态,取自 `~/wenqu/.deploy-state.archives`:

- `归档=ok` —— ACR 上有这份,本机删掉随时能拉回;
- `归档=fail` 或 `查无` —— **删掉后只能从代码重建,先补推再删**。

注意公共层是共享的,删旧 tag 通常只回收代码层那点空间,别指望清出几个 GB。

### 8.2 备份保留

按 `BACKUP_KEEP`(默认 7)报出超出的目录及其大小,并打印一条 `rm -rf`。改份数:workflow 的 deploy job 加
`BACKUP_KEEP: "14"`,或人工跑时前置环境变量。`backup.sh` 每次备份成功后也顺带报一次(同一脚本、同一口径)。
注意备份频率 = 发布频率:长期不发布就没有新备份,需要日备份得另配 cron(尚未纳入本链路)。
这些目录是唯一的离线保险,脚本永远不会代你删。

### 8.3 构建缓存(门 0 会自动清,人工也可主动清)

`docker build` 的层缓存只增不减,通常是最大的一块。门 0 在水位不足时会自动回收(先 7 天未用、再全部);
想主动回收不等发布:

```bash
docker builder prune -f --filter "until=720h"
```

代价:清完后的**第一次**发布 build 会变慢(缓存要重建,你这台 2 核机上尤其明显),运行中的服务不受影响。

## 9. 一键演示（OPT-46）：把生产开成"面试官能自己点开体验"

用途：有人要看系统时，让生产站进入演示态 —— 登录页出现"一键体验"，观众用演示账号进去就能看到
22 篇已经入库的文档，或者直接让脚本驱动真浏览器自动走一遍新用户路径并出截图。
设计口径见 `docs/设计-OPT46-演示模式.md`。

### 9.1 开（四步，第 1、2 步只能在生产机上做）

```bash
# 1) 生产机 ~/wenqu/.env 加两行(密码 ≥8 位,只用于演示,不得复用其它账号的密码)
APP_DEMO_MODE=1
APP_DEMO_PASSWORD=<演示专用密码>

# 2) 走一次正常 CD 发布(§7:手动 workflow_dispatch + 版本号复述),让镜像带上这段代码
#    开关是配置,不改数据库 —— 本功能零迁移、零回滚负担。
```

```bash
# 3) 从讲解机播种数据(脚本只打 HTTP,所以能在自己电脑上对着生产跑)
#    两个环境变量都得给:脚本自己也要 APP_DEMO_MODE=1(防误跑的保险),密码用于注册/登录。
#    这一步真的走 22 篇文档的向量化,要等几分钟;服务端的 worker/parser 必须在跑。
cd server && WENQU_BASE_URL=http://<SERVER_IP> \
  APP_DEMO_MODE=1 APP_DEMO_PASSWORD=<同上> \
  uv run python scripts/seed_demo.py
```

```bash
# 4) 验证 + （可选）自动演示
curl -s http://<SERVER_IP>/api/v1/demo/status   # 期望 enabled=true、ready=true、document_total=22(跑过 --live 之后是 23)
make demo-browser                                   # 装一次浏览器内核,约 150MB,只需一次
WENQU_BASE_URL=http://<SERVER_IP> APP_DEMO_PASSWORD=<同上> \
  make demo-run ARGS="--headed -n 6"                # 密码不给脚本 preflight 会拒绝启动
```

`ready=false` 时登录页只会显示"演示数据未就绪 + 入库进度"，不会放出"一键体验" —— 这是故意的，
别为了让入口出现而提前改前端。

### 9.2 关

生产机 `.env` 把 `APP_DEMO_MODE=0`，重启 server。演示数据可以留着（幂等，重跑不会重复建），
也可以连着两个环境变量一起给，删掉演示空间（**演示账号保留**，只删那个名字的空间）：

```bash
cd server && WENQU_BASE_URL=http://<SERVER_IP> \
  APP_DEMO_MODE=1 APP_DEMO_PASSWORD=<演示密码> \
  uv run python scripts/seed_demo.py --purge
```

### 9.3 故障对照（会不会影响正常业务）

| 现象 | 真原因 | 处置 |
|---|---|---|
| `/demo/status` 返回 404 | 这个版本的服务还没带 OPT-46（没发布，或打到旧镜像） | 按 §7 发布一次。**不影响任何既有功能** |
| 返回 200 但 `enabled=false` | 服务端 `APP_DEMO_MODE` 没生效（改了 `.env` 没重启，或改的不是那份 `.env`） | 重启 server 后复测 |
| `enabled=true`、`ready=false`、`document_total=0` | 没跑过 seed，或 seed 中途失败 | 跑第 3 步；报错信息里已写明缺哪个前提 |
| seed 卡在"等文档入库" | worker 或 parser 没在跑（入库是异步的，没人消费就一直在队列里） | `docker compose ps` 看这两个容器 |
| 脚本提示"浏览器启动失败" | 没装 playwright 内核，或 playwright 版本与已装内核型号不匹配 | `make demo-browser`；版本钉在 `PLAYWRIGHT ?= playwright==1.60.0`（改版本要确认能下载对应 chromium） |
| 脚本某一步"等元素超时" | 有人改了演示路径上的元素，`data-testid`（页面元素上专门给自动化脚本用的标记属性）没了 | 对照 `docs/api/前端接入工单-OPT46演示模式.md` 附录 A 补回来 |

### 9.4 三条安全口径

1. **密码不进接口、不进日志**：`/demo/status` 只给用户名。演示密码泄露的后果限于那个演示空间，
   但它挂在你的生产站上 —— 用它自己的密码。
2. **截图里有明文 API Key**：自动演示会在"签发 API Key"那一步截屏（页面设计上明文只出现一次，
   这是要展示的点）。`demo-out/` 已进 `.gitignore`；对外分享截图前先删这张图，那把
   `demo-e2e-<时间戳>` 的 Key 用完吊销即可。
3. **开关默认关**：`APP_DEMO_MODE=0` 时这个端点对任何人只回 `enabled=false`，不透露用户名/空间名/文档数。
   不演示就关掉，少一个免登录的信息暴露面。

### 9.5 手动演示时两处"看着像坏了"的地方（都不影响功能）

| 现象 | 真原因 | 怎么办 |
|---|---|---|
| 切完空间再点侧栏，第一下没反应 | 切空间那个弹层没关，第一下点击被它吃掉了（自动演示脚本里已按"先点 Logo 关掉它"处理） | 再点一次，或先点一下页面空白处 |
| 发出问题后发送按钮一直是灰的 | 它要求输入框里有字才算可点，而发送后输入框就清空了 | 正常。生成中的标志是旁边那个「停止生成」按钮，不是发送按钮 |
