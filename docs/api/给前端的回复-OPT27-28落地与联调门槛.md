## 4. OPT-29:契约预告 + 需要你们回应的一个决策

后端剩余工作(29b 生成链路取值 → 29c `messages` 透出 → 29d 集成测试 → 29e 契约重导),

口径会按你们 §3.2 的渲染规则实现,三点先说清楚:

1. **分子**:本轮**最后一次**上游调用的 prompt+completion。直检模式就是一次调用;
   Agent 模式一轮提问会打多次上游(工具轮/作答轮),累加会重复计数(每轮都重发上下文),
   所以取"作答那次" —— 它上下文最全,进度条要的就是这个。无检索结果的兜底回答
   **没打模型**,两值为 null。
2. **分母**:本轮实际解析到的 chat 模型的 `context_tokens`。空间层必填,全局层历史值可为空
   (用户裁决"可以留空")→ 此时 used 有值、window 为 null,走你们"窗口未配置"分支。
3. **null 组合约定**:两值同时 null = 老消息/本轮没调模型;used 有值 + window null = 模型没配
   窗口;**used null + window 有值后端不会出现**,出现请当 bug 报。`partial=true`(断线宽限截止)
   的 done 帧**也会带**这两值。

**要你们回一个问题(越早越好,后端下一步就要写代码)**:进度条要不要区分"厂商实测 / 本地估算"?

- 后端优先用厂商回传的 `usage`,厂商没回时才按 0.75/0.25 估算,**目前契约里不区分**(就两个 int);
- 我们的建议:**进度条不加标记**(它是仪表,±10% 不影响"要不要新开会话"的决策;≈ 留给 §2 用量页
  那个账单口径,那里必须区分);
- 如果你们要区分,现在还来得及在 done 帧加一个 `context_usage_estimated: bool`(加法式,不破契约),
  `messages` 侧则要多一列。**请在后端 29b 动工前答复,过期按"不加"实现。**

另外提醒一条已登记的待办(**OPT-32**,见 `docs/优化台账.md` §2;原写 OPT-31,已按你们 §3 的撞车提醒改号):
