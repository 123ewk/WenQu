## 2. 发现明细

### F1(口径不符)PATCH models 的 `context_tokens:null` 返回 200 但值不变

- 请求:`PATCH /spaces/{sid}/model-config/models/{pk}` body `{"context_tokens": null}` → **200**,回包仍 `64000`;
- 影响:「窗口未配置」态在 dev 无任何 API 路径可造(POST 必填 422),前端实测只能依赖你们单测钉住;
- 期望明确:PATCH 三态语义(omit=不改 / null=?)。若 null=不改,请写进对接说明(我们按"不可清除"实现);若 null=清除,请修;
- 复现:上述 curl 即可。

### F2(口径不符)`dashscope_rerank` 默认端点与上游真实端点不匹配,重排"生效"不可观测

- 请求:`POST .../providers/{百炼重排}/test` → **424 `UPSTREAM_MODEL_ERROR` `details.reason="model_name"`**
  (base_url 取类型默认 `https://dashscope.aliyuncs.com/compatible-mode/v1`,模型名 `gte-rerank`);
- 检索对照(2 命中,query「合同审批的金额分界」):开关 ON/OFF 两次 `POST /retrieval/search` 排序与 `score` **逐字节一致**(RRF 0.0164/0.0161),且契约命中行**没有 rerank 分字段** → 即便上游修好,前端也从响应上区分不出"重排参与与否";
- 期望:① 类型表里 `dashscope_rerank` 的 default_base_url/探活路径对上真端点;② 若希望"生效"可验收,给检索命中行加一个重排可见性字段(契约变更说明先行);
- 前端侧:424 reason 文案直显已按 §1.6 实现,降级链路(开关 ON 但检索不报错)行为正确。
