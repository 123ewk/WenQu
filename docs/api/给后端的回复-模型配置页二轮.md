## 4. 发现

**F1|已下线模型 `gte-rerank` 的【测试模型】错误类别被误报为「Key 无效」——判:后端**
- 空间/供应商:二轮联调空间A / `prod-bailian-rerank`(真 Key)。
- 现象:填 `gte-rerank`(无 -v2,2026-05-30 下线)→ 保存 201 →【测试】显示「测试失败:Key 无效」,与需求单 §7④ 预期的"上游 model_name 类错误"不符,会误导用户去查 Key。
- 复现:该供应商下建模型名 `gte-rerank` → POST `/model-config/models/{pk}/test`。
- 后端原始响应:`424 {"code":"UPSTREAM_MODEL_ERROR","message":"Key 无效或权限不足","details":{"reason":"auth"}}`。
- 根因取证:直连百炼原生端点复现 → 上游对 `gte-rerank` 实际返回 **HTTP 403 `AccessDenied`**("Access denied. For details, see .../error-code#access-denied"),
  同 Key 同端点 `gte-rerank-v2` 返回 200。即后端 `space_models.py:628-634` 的 `status in (401,403)→auth` 映射忠实按状态码分诊,
  但**百炼对"下线模型"的语义用的是 403**,与"Key 无效"共享状态码。
- 期望:百炼协议下 403 若响应体含 `AccessDenied` + 模型类 detail,可细分到 `model_name`(或 message 加"或模型不可用");
  至少文档口径注明"百炼下线模型报 auth 属已知映射"。前端展示逻辑无需改(忠实透显 message)。
- 影响:低(不阻塞验收;提示文案里已前置警告"填它上游必报错")。

**F2|模型名预设反推类型依赖 base_url 全等——判:前端(已登记,待后端字段解除)**
- 见 §2 疑问 1。现象:base_url 被改过的供应商无预设(退化纯输入框,当前唯一可观测行为,可接受)。
- 期望:`SpaceProviderOut` 补 `provider_type` 后前端删除启发式。复现:任一供应商 PATCH 改 base_url → 其模型弹窗预设消失。

**F3|侧栏空间列表不随外部新建空间自动刷新——判:前端(边缘,超出本单范围)**
- 现象:空间 B 经 API 创建后,侧栏切换菜单仍只有 A,`location.reload()` 后出现。
- 复现:API `POST /spaces` → 点空间按钮。前端仅在登录/手动刷新时重拉 `GET /spaces`;正常经 UI「新建空间」流程会即时刷新,故实际影响≈0。
- 建议:可下轮把新建空间成功回调接入 store 更新;本单不改(非必要不动)。
