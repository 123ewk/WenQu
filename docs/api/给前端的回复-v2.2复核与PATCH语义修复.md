## 2. PATCH 语义修复(§9.6)

**修了什么**:`PATCH /api/v1/spaces/{id}` 的字段语义对齐 REST 惯例 ——

| 请求形态 | 修复前 | 修复后 |
|---|---|---|
| `description` **省略** | 清成空串 ❌ | **不改动** ✅ |
| `description: ""` | 清空 | 清空(不变) |
| `retrieval_params` 省略 | 不改动 | 不改动(不变) |

- 代码:`UpdateSpaceRequest.description` 改为可选可空(`str | None`,省略=None),
  服务层判 None 跳过赋值;`name` 仍必填(改名是本接口的主语义,不变);
- 契约:`UpdateSpaceRequest.description` 由 `type: string, default: ""` 变为可空 anyOf
  (`openapi.json` 已重导,提交 `098cc68`)——纯放宽,现有类型生成不会报错;
- **前端可以简化了**:"保存检索参数时把当前 name/description 一并提交(防清空描述)"
  的规避写法不再必要,后续迭代可去掉一并提交的逻辑(不去掉也完全兼容);
- 测试:单测(省略保留/显式清空)+ 集成(省略只改名 → 描述保持;显式 "" → 清空)。
