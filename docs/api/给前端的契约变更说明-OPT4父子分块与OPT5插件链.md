# 契约变更说明:OPT-4 父子分块 & OPT-5 问答插件链化(给前端)

> **一句话:好消息 —— 设计落定后 OPT-4 对你们是"零代码改动 + 一轮回归",OPT-5 是"零影响"。**
> 台账里预告过"OPT-4 会改引用载荷形态",实际设计做到了**载荷完全兼容**(见 §1.2),
> 所以前端从"改造"降级为"回归验证"。机器契约以 `docs/api/openapi.json` 为准。
>
> 对应后端提交:本说明为变更预告,后续按 §4 的提交序列逐个落地。

---

## 1. OPT-4 父子分块(检索命子块、返回父块)

### 1.1 设计落点

- **父块** = 你们现在已经在看到的"块":小节级、≤512 token、带面包屑头。
  分块列表页、引用抽屉"查看完整原文"、`chunk_count` 统计看到的**仍然是父块**,没有第二种"块"出现。
- **子块** = 父块内部更细的检索窗口(默认 ≤256 token),**只活在检索索引里**:
  向量与全文匹配都打在子块上,命中后回取父块组装结果。
  子块不会出现在分块列表、引用、抽屉的任何位置 —— 前端感知不到它的存在。

### 1.2 为什么载荷不用改(与预告的差异)

| 前端消费点 | 现行 | OPT-4 之后 | 变化 |
|---|---|---|---|
| SSE `citations[].chunk_id` | 命中块的 id | **父块** id | 无(语义一致:抽屉按它取全文) |
| `citations[].excerpt` | 内容前 300 字 | 父块内容前 300 字 | 无 |
| `citations[].breadcrumb/page/filename/score` | 现行 | 父块的 meta;score 是子块匹配分 | 无 |
| 分块列表 `GET .../chunks` | 分页块列表 | 只返回父块(子块不出现) | 无 |
| 检索测试 `SearchResult` | chunk_id/content/meta | chunk_id=父块,content=父块内容 | 无 |
| `citations` 里的重复引用 | 不会出现 | **同一父块的多个子块命中会去重成一个引用** | 无(更干净) |

预告说"会改载荷形态",是因为当时按"citations 指向子块"设想;落定设计选择了
**citations 指向父块**,所有形状保持原样。效果:答案的生成上下文与引用抽屉看到的是
同一段(父块)全文,子块只提升"搜得准"。

### 1.3 两处口径变化(都是统计口径,不是字段)

1. `chunk_count`(知识库聚合统计)与分块列表的 `total`:**只统计父块**。
   一份文档入库后的可见块数与今天同口径;检索索引里的子块数不进任何对外数字。
2. `POST /api/v1/chunks/preview` 响应项**新增可选字段** `children: ChunkPreviewItem[]`
   (父块内子块的预览;未触发切分时为空数组)。加法式变更,现有渲染不受影响;
   后续做分块调参 UI 时可以用它展示"父块 → 子块"两层结构。

### 1.4 存量数据(与面包屑修复同口径)

已入库文档的检索仍在**父块级**匹配(与今天等价,不会变差也不会变好);
要对某份文档启用父子分块,触发"重新解析"重建索引即可(旧块会被整体重建)。

## 2. OPT-5 问答流水线插件链化

纯后端内部重构:把现行硬编码的 检索 → 组装 → 生成 → 引用 流程拆成插件链,
**阶段边界不变、SSE 事件形态不变、错误码不变** —— 前端无任何动作。
若实现中发现必须动事件形态,会**另发补充说明并等你们排期**,不会偷改。

---

## 3. 前端要做的

1. **现在:什么都不用改**,本说明只是预告;
2. OPT-4 落地后:跑一轮**引用抽屉回归**(角标 [n] → 抽屉 excerpt → "查看完整原文"全文),
   顺带确认检索测试页表现正常;
3. 下次从 openapi.json 重新生成类型时,`ChunkPreviewItem` 会多出 `children?`
   (可忽略;想做分块调参展示时再用)。

## 4. 后端落地序列(每步独立提交,契约门禁把关)

1. `feat(chunking)`:分块器产出父子两层块(含 preview 接口 children 字段);
2. `feat(ingestion)`:流水线写父子块,仅子块进向量/全文索引;统计口径切父块;
3. `feat(retrieval)`:命中子块回取父块 + 同父块引用去重;
4. `chore(contract)`:openapi 重导 + 契约测试更新;
5. `docs`:两台账与接口说明同步。

有任何与本文不符的实测结果,按对接标准 §2 的规则:以实测为准,写回缺口清单并同步后端。
