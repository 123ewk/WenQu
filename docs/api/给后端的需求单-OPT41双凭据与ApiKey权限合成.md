## 2. 现状：认证与授权怎么走（带行号）

### 2.1 两个入口，二选一
```
请求 → get_current_actor (app/api/deps.py:111-128)
        ├─ 有 X-API-Key → get_api_key_principal → Key 链路，Caller.user = 绑定成员
        └─ 无           → get_current_user (deps.py:79-90) → JWT 链路，Caller.api_key = None
```
- `deps.py:122` 是分叉：只有带 Key 才进 Key 那套校验；两个都没有 → 401；两个都带 → Key 优先，**不做"两个都要"的校验**（R1 不成立的根因）。
- 设计意图见 `api/api_key_auth.py:5-8` 与 `docs/架构设计.md:331-336`「两个认证入口并存：JWT（人用）与 API Key（程序用）」→ **本需求是改授权模型，不是修 bug**。
- 网页端全用 JWT，**没有一处发 `X-API-Key`** → 生产上"不带 Key 也能问答"走的就是这条。

### 2.2 Key 链路的四层校验
| 层 | 代码 | 语义 | 失败 |
|---|---|---|---|
| ① 认证 | `application/service/api_keys.py:230-249` | 前缀 → SHA-256 哈希命中 → 未吊销 → **绑定成员仍在 Key 自己的空间** | 401 |
| ② 路由授权表 | `api/api_key_auth.py:44-96` | **fail-closed 白名单**，未登记的 (路径,方法) 一律拒 | 403 |
| ③ 能力 | `api_keys.py:253-260` | `capabilities` 必须含所需能力；**空 = 什么都不允许**（fail-**closed**） | 403 |
| ④ KB 范围 | `api_keys.py:262-283` | **空 = 不限 KB**（fail-**open**）；非空则与请求求交，交集空 → 403 | 403 |

授权表现量（`api_key_auth.py:44-86`）：`chat` = 3 条（`/ask`、`/retrieval/search`、续流 `GET .../stream`）；`documents` = 9 条（KB 列表/详情、文档增删查、chunks 只读、reparse）。新增路由不自动对 Key 开放 —— **保留这个好设计**。

### 2.3 成员身份这一侧
- `domain/enums.py` `Role.VIEWER=10 / EDITOR=20 / ADMIN=30 / OWNER=40`；各服务自查，如问答 `qa.py:244` → `_require_member`（`:500-506`，只要求 `role ≥ VIEWER`）。
- **成员侧无 KB 粒度**：`domain/models.py:151-175` `KnowledgeBase` 只有 `space_id / name / embedding_model / created_by`，无"谁能看"字段 → 成员对本空间**所有库全可见**。
  **→ 用户拍板：库的粒度全部交给 Key**（§0 第一轮第 1 条）。

### 2.4 现状合成公式
`可用 = Key(能力 ∩ 路由表 ∩ kb_ids) ∩ 绑定成员的角色` —— 带 Key 时已是交集；不带 Key 时 Key 那一半整个不存在。

## 3. 差距清单（G1–G7）

### 🔴 G1　只带 JWT 就能问答/检索/上传 —— 用户报的现象
`deps.py:111-128`、`routes/conversations.py:186-214`、`routes/retrieval.py:81-100`。→ `kb_ids` 对人完全无效，网页端能检索空间内任意库。**R1/R2 靶心。**

### 🔴 G2　Key 与"路径里的空间"没有绑定校验（跨空间越权）
`get_api_key_principal` 造了 `ApiKeyPrincipal(space_id=api_key.space_id)`（`api_key_auth.py:168`），但**全仓库没有任何地方读它**（`grep 'principal\.space_id'` = 0 命中）。`/ask` 只校验"绑定成员 ∈ 路径空间"（`qa.py:244`）。
推论（**代码走读，未实测**）：某人同时在 A、B → A 签的 Key 能打 B；Key 的 `kb_ids` 为空时 `resolve_kb_scope` 返回 `None`（`api_keys.py:271-272`）→ 检索只剩 `Chunk.space_id == B` 一个谓词（`application/repository/retrieval.py:45,74`）→ **B 全库可读**。`kb_ids` 非空时因 A 的库 ∩ B 的空间恒空而"看起来挡住了"，**那是巧合不是防线**。
→ 一把 Key 绑多成员之后这条**更危险**（一把 Key 泄露/给多 = 波及多个人的全部可及空间），N2 必须与 N11 同批或更早。

### 🟠 G3　"范围空 = 全部"是 fail-open，与"能力空 = 全拒"两套口径打架
`api_keys.py:253-260`（空=全拒）vs `:262-283`（空=全放），`domain/models.py:348-349` 两行注释并排写着相反语义。
→ 不勾库 = 给了全库权限，界面上看着像"什么都没选"。**R2 落地后这条最致命**（Key 是唯一数据防线，默认却全开）。→ N3。

### 🟠 G5　`is_active`（OPT-31）现在不参与认证
`api_keys.py:179-218`，注释 `:184-185` 原文「纯管理标记：不参与 authenticate 热路径」。
→ R4 要求"配好即绑定"有实际效力 → **`is_active` 在人链路升级为硬开关**（N7）。**注意：R6-b（多成员绑定）会把这个字段连带重构，见 N11 第 2 条。**

### 🟠 G6　签发门槛：成员不能自助建 Key，明文只回显一次
`api_keys.py:92/162/188` 三处 `_require_role(..., Role.ADMIN)`；明文只在创建响应出现一次（`:101-126`）。
→ 与 R4 一致（Admin 配、成员不填），**因此明文不需要进浏览器**。

### ⚪ G7（附带）会话读端点对纯 Key 客户端不可用
`routes/conversations.py` 里 `get_current_user` 6 处 vs `get_current_actor` 3 处 —— `GET /conversations`、`GET .../messages`、`PATCH`、`DELETE` 只挂 JWT 依赖且未登记授权表。程序化客户端能问能续流，但**列不出会话、翻不了历史**（N9）。

### ✅ G4　成员侧 KB 粒度缺失 —— 按拍板不再算差距
用户明确"库的权限由 Key 管"。原 N5（成员 KB ACL 新表）移出本批。**但前提要写死**：正因为 Key 是唯一数据范围来源，**"成员一把 Key 都没有"必须等于"什么都检索不到"**（而不是"能检索全空间"）—— 这正是 N3 要把 fail-open 翻成 fail-closed 的核心理由。

## 4. 权限合成口径：**A（全交集）已定稿**

### 4.1 公式
```
存在性门槛：成员身份有效（仍在空间）  ∧  生效 API Key 存在且可用
            —— 人：JWT + 服务端解析"该成员当前生效的那把 Key"
            —— 程序：X-API-Key 明文

动作（能不能调这个接口）：成员角色档位  ∩  Key 能力
数据范围（能读哪些库）：  成员可见库(=本空间全部)  ∩  Key.kb_ids / all_kbs   ← 实际由 Key 决定
```
**与 C 的唯一区别**：Key 上没勾的能力，**人在网页上也做不了**。例：成员是 Editor，生效 Key 只有 `chat` → 上传文档 **403**（C 下是允许）。

### 4.2 ⚠️ A 必须限定边界，否则会把管理员锁死（实现约束，不是待议项）
"动作取交集"如果**无差别套到所有接口**，会得到荒谬结果：没有任何 Key 的能力覆盖"管理成员""建 Key""配模型"（授权表里根本没有这些路由，`api_key_auth.py:44-86` 只有 `chat`/`documents`）→ **Admin 连给自己建一把 Key 的入口都没有，空间直接失去管理**。

所以 A 的适用边界必须写成硬约束：
1. **交集只作用在「双凭据强制清单」内的接口**（一期 = `/ask`、`/search`、文档增删/重解析，即 Q2 已定范围）；
2. **清单外的接口继续只看成员角色**，Key 不参与判断 —— 包括空间管理、成员管理、API Key 管理、模型配置、`/admin/*`；
3. 路由授权表（层②）**继续只约束明文 Key 调用**，不约束人 —— 否则"模型配置是人的决定"这条既有例外（`docs/架构设计.md:340-345`）会被绕开；
4. 因此需要一张**「接口 → 所需能力」映射表**（清单内接口用哪档能力判定），建议直接复用 `_ROUTE_CAPABILITIES` 的反向视图，避免两套清单漂移。

### 4.3 运维含义（A 的代价，请知悉）
A 之下 **Key 就是那个人的实际权限**，角色档位只是上限。所以：
- 给成员配 Key 时必须**按他实际要在网页上做的事把能力勾全**（要问答 → `chat`；要传文档 → `documents`）；漏勾 = 他连日常操作都做不了，且**错误提示必须说清是"Key 没这个能力"而不是"你角色不够"**（N10 错误码要分两类）。
- 好处：权限只有一处真相（Key），符合"一把 Key 代表一种权限"（R6-b）。

## 5. 需求清单（N1–N12）

### N1　双凭据强制（R1 主体）—— 明文不进浏览器
- **要什么**：§4.2 清单内的接口，没有"生效 Key"即拒绝。人这条链路的生效 Key 由**服务端解析**：`JWT 成员 → 该成员在本空间被分配且当前生效的那把未吊销 Key`。请求**不需要也不应该**携带 Key 明文。
- **错误码**：`403` + 新 `code: "api_key_required"`（**不要用 401** —— 人确实登录了，401 会把前端踢成"重新登录"，且本仓库 401 有"仅登录路径"的审计过滤口径）。
- **实现位置**：`Caller`（`deps.py:100-108`）要多带"生效 Key"；建议作为 N4 合成器的输出，**不要在 6 个路由里各写一遍 `if caller.api_key is not None`**。
- **灰度**：配置开关（如 `APP_REQUIRE_API_KEY_FOR_CORE=0/1`，默认 0），因为 Q6 选了"无 Key 即全禁"，**上线那一刻所有真人成员都会掉进禁用态**，必须先给全员配好 Key 再打开。
- **验收**：① 只带 JWT、无生效 Key → 403 `api_key_required`；② 只带 JWT、有生效 Key 且范围含 KB1 → 只能命中 KB1；③ 只带明文 Key → 与今天一致（程序化零回归）；④ 403 落被拒审计；⑤ 网页实测正常，且 **Network 里看不到任何 `sk-live-` 明文**。

### N2　Key 绑定路径空间（G2，纯加固，建议第一批就做）
- **要什么**：Key 链路（含 N1 解析出的"人的生效 Key"）若路径 `{space_id}` ≠ `api_key.space_id` → **403**（沿用 `api_keys.py:277-282` 的 403 口径，不要退化成 404）。
- **验收**：A 空间 Key 打 `/spaces/B/ask` → 403；空 `kb_ids` 的 Key 打 B → 403（今天会 200 并返回 B 的命中）。测试补 `server/tests/test_api_key_integration.py`（现有 `:411 / :392` 只测了跨空间吊销 404，**没有跨空间调用**）。

### N3　`kb_ids` 空语义翻成 fail-closed（R2 地基）
- **要什么**：`kb_ids` 空 = **不允许任何知识库**（与 `capabilities` 同构）。"全部库"用显式布尔 **`all_kbs`**（Q4 已定）。
- **配套（必须同批）**：① 迁移回填 `kb_ids = '[]'` 的旧行为 `all_kbs = true`（**零行为变化**，避免生产已签 Key 当场失效）；② 新签默认 `all_kbs = false`；③ 前端把"全部知识库"做成**要主动勾选**的选项并写清风险（`web/src/views/apiKeys/ApiKeysView.vue`）；④ 先出契约变更说明。
- **`all_kbs` 展开时机**：**每次请求实时展开成当时空间内全部 KB**，不要把快照存进 Key（否则新建的库永远进不来）。
- **验收**：新签 Key 不勾库 → 检索/问答 403；存量 Key 行为不变（回归用例）；`openapi.json` 重导 + `REQUIRED_PATHS` 门禁过。

### N4　统一权限合成器
- **要什么**：一个 `EffectivePermission` 入口，输入 `(成员角色, 生效Key.能力, kb_ids/all_kbs)`，输出 `{允许能力集, 允许的 kb_ids 集, 生效 key_id}`；路由与服务**只消费结果**。
- **为什么**：现在散在 `api_key_auth.py`（路由表）、`api_keys.py:253/262`、`qa.py:500`、`knowledge.py:138-162`、`conversations.py:198-199`、`retrieval.py:93-95` 六处。换成 §4.1 口径后散着改必然改漏。
- **验收**：`grep -c "resolve_kb_scope\|require_capability" app/api/routes/*.py` 命中数下降；§4.1 三口各有一组参数化用例钉住；§4.2 边界有专门用例（**Admin 无 Key 时仍能管成员/建 Key/配模型**）。

### N5　Key 的分配与"生效 Key"（R4）
- **要什么**：① 分配 = 现状已有（创建必填 `member_user_id`，`:93-97` 校验是成员，Admin+ 门槛 `:92`）——保留；② "配好即绑定" = 该成员当前生效的那把 Key 决定其权限（N1）；③ 切换见 N6。
- **一把成员有多把未吊销 Key 时取哪把**：取 `is_active = true` 的那把（部分唯一索引 `domain/models.py:359-365` 保证至多一把）。**若一把 `is_active` 都没有** → 由 Admin+ 为其激活一把（N6）；该成员在灰度开关打开后**核心功能不可用**（Q6 已定）。
- **不做**：成员自助申请/自建 Key（保持 Admin+ 门槛，符合"不需要它们自己填"）。

### N6　切换生效 Key = **只有 Admin+ 能做**（Q5 已定，成员不可自助）
- **要什么**：沿用现成的 `PUT /spaces/{sid}/api-keys/{kid}/activate`（`routes/api_keys.py:145-157`）+ 其 Admin+ 门槛（`api_keys.py:188`）。**不新增成员自助口径。**
- **要补的**：Admin 侧 UI 要能看到"某人当前生效的是哪把 / 无生效 Key"，并能一键换（前端 N10）。
- **生效范围**：**下一请求生效，不追溯历史消息**（已生成的回答引用的库不改写）。
- ⚠️ **与 R6-b 冲突点**：一把 Key 绑多成员后，"给某人换 Key"这个动作的落点从"Key 上的 `is_active`"变成"成员 ↔ Key 的归属关系"，**语义与索引都要重构**，见 N11 第 2 条。

### N7　`is_active` 的语义升级（G5）

- **运维提醒**：`activate` 从"台账标记"变成"权限开关"，**误点一次就改变某个人的可检索范围与可用动作** → 审计必须记全（N10）+ 前端二次确认。

### N8　Key 权限可编辑（R5，当前零口子）

- **审计**：新增 `AuditAction.API_KEY_UPDATED`（`domain/enums.py:74-76` 三条 `API_KEY_*` 旁边），detail 记**改前/改后**的能力与库数量 → 要能回答"谁把范围从 3 个库放到全部"。

### 🆕 N11　一把 Key 绑多个成员（R6-b）—— 这是权限模型升级，**要考虑的 12 件事**

> 本质：API Key 从"个人凭据"变成"**权限档位**"（成员挂到档位上，明文只是这个档位的程序化访问方式）。方向是好的（权限只有一处真相、改一次全员生效、正好满足 §4.3 的运维含义），但下面每一条都要有答案才动得了手。

1. **数据模型**：`api_keys.member_user_id` 是单列（`domain/models.py:375-377`，nullable FK `SET NULL`）→ 多成员需要**新关联表**（例：`api_key_members(api_key_id, user_id)`）+ 迁移 + 存量回填（每把 Key 把 `member_user_id` 落成一行）。
2. **🔴 OPT-31 的部分唯一索引要重做**：现在是 `uq_api_keys_one_active_per_member (space_id, member_user_id) WHERE is_active AND revoked_at IS NULL`（`models.py:359-365`），语义是"同成员至多一把正在使用"。一把 Key 绑多成员后 `is_active` 放在 Key 行上**语义就不成立了**（它同时对多个人生效）。→ `is_active` 必须**从 Key 挪到关联表的"成员选择"列**（例：`api_key_members(api_key_id, user_id, is_current)` + 部分唯一索引 `(space_id, user_id) WHERE is_current`）。**这是 N6/N7 的连带重构，OPT-31 刚交付的前后端都要改。**
3. **🔴 "人走 Key 停"这条安全保证会退化**：OPT-26 特意让 Key 绑单个成员，就是为了"成员被移出 → Key 在认证阶段即失效"（`api_keys.py:233-236、245`，`docs/架构设计.md:334-336`）。多成员后 Key 不再等价于某一个人 → 必须重新定义有效性判据（Q8：① 关联集合里**至少一个**成员仍在即有效；② 关联集合**全部**失效才无效；③ 移出成员时自动从关联表剔除，Key 与成员解耦）。**选错就等于把 OPT-26 的结论撤销了一半。**
4. **审计归因**：现在 principal = 绑定成员（`api_key_auth.py:165`），审计 actor 落到具体人。共享 Key 的**程序化调用无法知道是谁在用** → 审计只剩"这把 Key"。人这条链路不受影响（JWT 认得出人）。
5. **用量归因（OPT-28）**：`usage` 按 `(space_id, user_id)` 记（`deps.py:281、382` 传 `caller.user.id`）。共享 Key 的程序调用没有单一 user → 要么给用量表**加 `api_key_id` 维度**，要么规定"Key 必须指定一个归因成员（owner）"。不解决的话"谁把 token 花光了"查不出来。
6. **吊销爆炸半径**：吊销一把共享 Key 会**同时打断 N 个人 + 所有用这把明文的程序**；且明文只回显一次（`api_keys.py:101-126`），重签后要挨个通知使用方。→ N8（改权限）的价值因此更大：**优先用"改范围"而不是"吊销重签"**。
7. **个性化 vs 粗粒度**：共享档位下所有人的范围完全相同。某人需要更小范围 → 只能再建一把 Key（Key 数量膨胀）或给他单独档位。→ 需要一条约定：**"档位"按角色模板建（如"只读问答-产品库"），不要按人建**。
8. **权限提升风险**：Admin 把"张三的 Key"改成共享档位，等于把张三的范围给了别人；反之把共享档位范围放大，一次改动同时给多人扩权。→ N8 的审计必须记改前改后，且 `PATCH` 里**改成员集合与改权限建议分两个动作**（可分别授权/分别留痕）。
9. **谁能把自己挂到某把 Key 上**：必须是 Admin+（`api_keys.py:92` 同构），**绝不允许成员自助挂 Key** —— 那等于自己给自己提权（挂到一把范围更大的 Key 上）。这条要和 Q5 的结论一起写进契约。
10. **契约破坏性变更**：`ApiKeyOut.member_user_id / member`（`routes/api_keys.py:78-83、123-131`）→ 改成 `members: [...]`；前端分组展示、搜索、OPT-31 的四档过滤全要跟着改（N10 第 5 条）。
11. **迁移号与撞号**：新关联表要新迁移。**0017 已被 OPT-37（`provider_type`）预定**（`docs/优化台账.md:262`）→ 两件事必须排序，谁先动手谁取号，不得插号。
12. **是否干脆显式建模成"权限组"**：既然"一把 Key 代表一种权限"，更干净的做法是把概念正名：`permission_group(space_id, name, capabilities, kb_ids/all_kbs)`，成员→组（每人一个当前组），API Key → 组的**程序化凭据**（一个组可有多把明文 Key，轮换互不影响）。好处：人（JWT）和程序（Key）共用同一个权限源，`is_active` 的语义自然变成"成员当前挂哪个组"，第 2/3/6 条全部顺解；代价：改动面比"给 api_keys 加关联表"大，且要迁移现有 Key 数据。**我倾向这条**（见 Q7）。

### 🆕 N12　拉人时顺手配 Key（R6-a）
- **现状已支持一半**：建空间即自动 `Role.OWNER`（`application/service/spaces.py:34-47`），Owner ≥ Admin 满足建 Key 门槛；建 Key 要求目标**已是成员**（`api_keys.py:93-97`，`MEMBER_NOT_FOUND` 404）。

## 7. 现状取证（只读，不在生产留垃圾）

网页端登录后，用同一个 JWT 打**检索**（不要用 `/ask`，它会真的建会话和消息行）：
```bash
curl -sS -X POST "$BASE/api/v1/spaces/$SID/retrieval/search" \
  -H "Authorization: Bearer $JWT" -H 'content-type: application/json' \
  -d '{"query":"任意词","top_k":3}'
# 只带 Bearer、不带 X-API-Key → 200 且有命中  ⇒ G1 成立
```
对照组（Key 链路确实另有一套）：
```bash
curl -sS -X POST "$BASE/api/v1/spaces/$SID/retrieval/search" \
  -H "X-API-Key: sk-live-****" -H 'content-type: application/json' \
  -d '{"query":"任意词","top_k":3,"kb_ids":["<范围外KB>"]}'
# → 403 api_key_scope_denied（api_keys.py:277-282）
```
G2（跨空间）需要"某人同时在两个空间"的前提，**curl 复现不了**；要坐实我可以补一条一次性集成测试（不提交，跑完删）。
