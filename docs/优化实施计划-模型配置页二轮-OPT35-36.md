## 2. OPT-35:供应商行下发 `kinds`(给前端一个不用猜的分块依据)

### 2.1 契约变更(加法)

`GET /api/v1/spaces/{sid}/model-config/view` 的 `providers[]` 每项新增:

```jsonc
"kinds": ["chat"]        // 或 ["rerank"];开放ai_compatible 类 = ["chat"]
```

语义必须写清:这是**该供应商允许挂载的类别**(来自类型表),不是"当前实际挂了哪些 kind 的模型"。

### 2.2 为什么不能用"模型 kind 并集"

新建但还没加模型的供应商,并集为空 → 两个区块都不出现,正是当前痛点的翻版。类型 key 库里没存,
但 `protocol` 与 `kinds` 在类型表里是**一一对应的派生关系**,所以从类型表派生即可,零迁移。

### 2.3 实现要点

```python
# 协议 → 该协议允许的模型类别(从 PROVIDER_TYPES 派生,新增协议不用再抄清单)
_KINDS_BY_PROTOCOL: dict[str, tuple[str, ...]] = {}
for _t in PROVIDER_TYPES:
    _KINDS_BY_PROTOCOL[_t.protocol] = tuple(sorted(set(_KINDS_BY_PROTOCOL.get(_t.protocol, ())) | set(_t.kinds)))
```

- 放在 `space_models.py` 模块级,紧跟 `_TYPES_BY_KEY:121`;`view()` 的 `providers[]` 字典里加
  `"kinds": list(_KINDS_BY_PROTOCOL.get(p.protocol, ()))`。
- **未知协议不得静默**:`.get(..., ())` 会让一个手改库的陌生协议变成"两处都不出现"。
  本模块的协议一律来自注册表,库里出现未登记协议属于数据异常 → 取 `.get(p.protocol)` 为 `None` 时
  直接抛(或按 `_RERANK_PROTOCOLS` 之外的默认 `("chat",)` 并在注释里说明理由)。**二选一,别写两层兜底。**
- `SpaceProviderOut` 加 `kinds: list[str]`。**全局层 `/admin/model-providers` 不改**(它用的是另一套
  `ProviderOut`,见 §1):配置页只吃空间层聚合视图,全局层由超管后台用,没有分块需求,
  两边同时改只会多一处契约变更。

### 2.4 测试

- 单测/集成(`tests/test_space_model_config_routes_integration.py`):
  - 建 DeepSeek 供应商 → `view` 里该行 `kinds == ["chat"]`;
  - 建 `dashscope_rerank` 类型供应商 → 该行 `kinds == ["rerank"]`;
  - 建 `siliconflow_rerank` 供应商 → 同样 `["rerank"]`(证明不是"只认某个协议键");
  - 断言 `_KINDS_BY_PROTOCOL` 与 `PROVIDER_TYPES` 派生一致(防止后续加类型漏填 kinds)。
- 契约:`SpaceProviderOut` 字段数 +1 → openapi 断言与 drift 用例要跟着重导(见 §4)。

## 3. OPT-36:`/types` 下发模型名预设清单

### 3.1 契约变更(加法)

`GET /model-config/types` 每项新增:

```jsonc
"model_names": ["deepseek-chat", "deepseek-reasoner"]   // 提示清单,不是白名单
```

- **后端不校验** `model_name ∈ model_names`,继续只限长度(§1 事实)。自定义必须可用,这是需求硬条件。
- 空清单(本地类型可能给 `[]` 或指向模型库的少量示例)合法,前端按"无预设"渲染成纯输入框。

### 3.2 为什么是常量表,不是"去厂商拉一次模型列表"

1. 新建供应商时 Key 往往还没填,拉不到;
2. 并非所有厂商都有 `/models` 列表端点(百炼原生、豆包等的清单接口与鉴权各不相同);
3. 列表端点返回的是"这个 Key 能用哪些",与"人类常见的填法"不是一回事,而且会把上游延迟塞进配置页首屏。

→ 常量表随类型表一起维护。若以后确实要"带 Key 拉厂商清单",另开触发式条目,不混进本批。

### 3.3 预设清单(**上线前逐个核对厂商当前在售名,别照抄**)

建议初值(高置信、当前主流;厂商改名不影响功能,只影响提示新旧):

### 3.4 实现要点

- `ProviderType` 加 `model_names: tuple[str, ...]`(`space_models.py:68-80`),13 项逐个填;
  `provider_types()` 输出 `"model_names": list(t.model_names)`;`ProviderTypeOut` 加同名字段。
- 排序即前端下拉顺序:把"最该选的"放第一个,前端用 `allow-create` 时首位就是默认落点。
- **不新增校验、不新增错误码、不改请求体** —— 本条只影响两个只读响应。

## 7. as-built(2026-09-21 落地回写)

**状态:OPT-35 / OPT-36 均已落地,4 个本地提交,未推送。**
`64fb8cc` 契约变更说明(先发)→ `d077e47` OPT-35 → `427f476` OPT-36 → 本片(门禁 + openapi + 文档)。

与原计划的差异(都是动手时才发现的,按事实改口径):

1. **写端点的响应也带 `kinds`**:计划只说聚合视图,实际 `POST /providers` 与
   `PATCH /providers/{id}` 用的是同一个 `SpaceProviderOut`,少一处就 mypy 报缺参。
   所以取值的公开口是 `space_models.kinds_for_protocol(protocol)`,三处共用
   (计划里写的 `_KINDS_BY_PROTOCOL.get(...)` 内联式没有落地)。
2. **未知协议选了两选一里的后者**:返回空清单 + 注释说明语义(两区块都不列),
   **不抛错** —— 让一行脏数据把整个配置页读成 500 明显更糟。
3. **`model_names` 带默认值 `()`**:豆包/vLLM 这两项因此不用占行。
   豆包留空的理由比原计划更强:它要填的是控制台**逐账号自建的接入点 id**,给预设等于给错值。
4. **厂商名在线核对过的**:百炼侧 `gte-rerank-v2` / `qwen3-rerank`(`gte-rerank` 已下线,不入表)、
   Cohere `rerank-v3.5`(阿里云、Cohere 官方文档 2026-09 版)。
   带日期后缀的名字(`kimi-k2-0711-preview`、`MiniMax-Text-01`、`glm-4-plus`)没逐个核到当日版本,
   过期只影响提示新旧,不影响功能 —— 发现错的回信报出来按批更新。
5. **全局层 `/admin/model-providers` 确认不改**:它用自己的 `ProviderOut`,与空间层不共用。

门禁:ruff `src tests` 0 错、`mypy src` 0 错(74 文件)、全量 **403 passed**(本批 +2)、

## 8. F1 全链路闭环(2026-09-21 收尾批补记)

**F1 = 已下线模型 `gte-rerank` 的探活错误被显示成「Key 无效」**(百炼对它回 HTTP 403 `AccessDenied`,
与"Key 无权限"共用状态码)。闭环要**两端各改一处**,只做后端等于没做:

| 环节 | 提交 | 内容 |

| 环境 | dev :8000 重启到 `11ed8d8` 后代码 | throwaway 探针实测 `424 / reason=auth / message=Key 无效(鉴权失败)`(旧代码这句是"Key 无效或权限不足") |
| 复验 | `1e62a0a` 三条页面原文 | ①`gte-rerank-v2`「调用正常」②`gte-rerank`「Key 权限不足,或该模型不可用(未开通/已下线)」③不可解析域名「网络不通或 base_url 有误」 |
| 补最后半支 | `b3daa3b` | 「上游返回异常(status=…)」dev 无稳定 429 上游 → 用测试里现成的可控假上游 `_ProbeAdapter` 断言 message 含 `status=429`(负向对照:改成 `status=999` 即 FAILED)。不改 `_upstream_error` |

已在处置单头部勘误;历史来信里的同类表述按事实读,勿再据此判断。
