## 1. V1 范围与"完整链路"的定义

**V1 = M1(账号与空间)+ M2(核心 RAG 闭环)后端全链路 + 前端 L0 对接。**

"完整链路跑通"指下面这条链路端到端可用(已由冒烟脚本实测,见 §3):

```
注册/登录 → 建空间(多租户隔离) → 建知识库 → 上传文档
  → [异步] 解析 → 分块 → 向量化 → 索引
  → 混合检索(向量 ∥ 全文,RRF 融合)
  → 流式问答(SSE)→ 答案带引用 → 引用可回溯到原文块
```

**V1 明确不包含**(不影响"链路完整"的判定,均属后续优化):
Agent 工具调用、多副本、rerank。
(API Key 程序化接入、SSE 断线续流、父子分块、问答插件链化原在此清单,均已交付。)
逐项来源、延后理由与触发条件见 **`docs/优化台账.md`**。

## 4. 后端为前端提供的 L0 能力(契约基线快照)

**认证**:`POST /auth/register|login|refresh|logout|switch-space`
**用户**:`GET|PATCH /users/me`、`POST /users/me/password`、`GET|POST|DELETE /users/me/avatar`
**模型**:`GET /models`
**空间**:`GET|POST /spaces`、`GET|PATCH|DELETE /spaces/{id}`、`POST /spaces/{id}/leave`、`GET /spaces/{id}/ingestion-progress`
**成员**:`GET|POST /spaces/{id}/members`、`PATCH|DELETE /spaces/{id}/members/{user_id}`
**审计**:`GET /spaces/{id}/audit-logs`(支持 `action`/`actor_id`/`since`/`until` 筛选)
**知识库**:`GET|POST|PATCH|DELETE /spaces/{id}/knowledge-bases[/{kb_id}]`(含聚合统计)
**文档**:`GET|POST .../documents`、`GET|DELETE .../documents/{doc_id}`、`POST .../reparse`
**分块**:`GET .../documents/{doc_id}/chunks`、`GET .../chunks/{chunk_id}`、`POST /chunks/preview`(父子分块 OPT-4:列表与统计只含父块;preview 加法式返回 `children` 检索窗口层)
**检索**:`POST /spaces/{id}/retrieval/search`(支持请求级调参)
**会话问答**:`GET|POST /spaces/{id}/conversations`、`PATCH|DELETE .../conversations/{cid}`、`GET .../messages`、`POST /spaces/{id}/ask`(SSE)、`GET .../conversations/{cid}/stream?after=<seq>`(断线续流,OPT-3,可选增强)
**API Key**:`GET|POST /spaces/{id}/api-keys`、`DELETE /spaces/{id}/api-keys/{key_id}`(明文仅创建响应一次;能力级授权 + KB 范围收窄,见 `docs/api/m3-api-keys-接口说明.md`)
**系统**:`GET /health`、`GET /system/info`(根路径,不带 `/api/v1`)

逐字段以 `docs/api/openapi.json` 为准;流程与边界见 `docs/api/` 下各接口说明文档
(m1/m2 基础说明、两轮补齐说明与 L0 收尾工单;历史快照类公告已清理)。

## 6. 已修正的实现缺陷记录(按发现渠道)

| 缺陷 | 发现方式 | 实际原因 | 修正 |
|---|---|---|---|
| 分块过散:一个小节被按段落切成多个碎块 | 用户反馈"chunk 太散" | 装块粒度取成了**段落**,而段落只是排版单位 | 改为**小节级装块**(不超上限即一块),超了按 段落→行→句→子句→字符 递归切;实测同一份简历 36 块 → 7 块(中位 375 token) |
| 分块面包屑出现同级标题、内容错位 | 用户上传真实简历 PDF 后肉眼发现 | PDF 解析把整页 span 拍平后**跨行**按字号相近合并,多行粘成一个"标题" | 以 pymupdf 的 line 为原子单位;逐行判定标题(长度 ≤40 字 + 不以句末标点/逗号结尾),连续同字号正文合并为段落 |
| 标题层级全部塌成 1/2 | 同一轮排查 | `level = 1 if size >= body*1.5 else 2`,且基准字号取**全部 span 中位数(含标题)** | 基准字号按**字符量加权**取众数;标题候选字号去重降序编号 1..N(上限 6) |
| 表格块被排到页尾 | 排查时实测 | 表格先于文字块产出,未参与排序 | 与文本行按 y 坐标统一排序 |
| 合并碎块后面包屑头重复 N 次 | 修复后复跑真实 PDF 发现 | `_merge_tiny` 直接拼 `content`,而 content 已含面包屑头 | `ChunkDraft` 保留 `body`,合并后 `render()` 重算 |
| 大字号长段落被判成标题而整段丢失 | reviewer 子代理审查 | 旧代码有 `len(text) <= 80` 兜底,重写时漏掉;chunking 不为标题产出块 | 恢复长度上限(40)并加句末标点判定;补测试 |
| `/ask` 显式选对话模型必 503 | 前端实测(缺口台账 §11.2-1) | 回答模型 id 被同时喂给检索向量化(要求 embedding 类型) | 检索向量改取目标 KB 的 `embedding_model`;请求 `model_id` 只驱动回答(SearchRequest.model_id 废弃保留) |
| 损坏图片上传返回 500(应 415) | 前端实测(§11.2-2) | PIL 对个别损坏图片抛 `SyntaxError`,不在捕获列表 | 捕获列表补 `SyntaxError`,归一 415;补单测 |
| `ChunkOut.tokens` 恒为 null | 前端实测(§11.2-4) | 入库流水线漏把分块 tokens 写进 chunk meta | tokens 随 meta 落库(存量文档 reparse 后有值);补单测 |

> 口径:本表记**实现与预期不符**(代码 bug);§5 记**文档与实现不符**。两者都要登记,避免同一处反复被采信。
> 存量已入库文档的面包屑是旧逻辑产物,需对文档触发重新解析才会修正(已用真实简历 PDF 验证:36 块 / 4 种面包屑 / 无头重复)。

## 7. 维护规则(交付侧)

- **模块增减或职责变化** → 更新 §2(以实际目录为准,不要照抄规划图);
- **每次大改动后重跑 §3 的命令**,用实测值覆盖旧值,勿手改估算值;
- **新增/下线契约端点** → 同步 §4 快照与 `docs/api/openapi.json`;
- **再次发现"文档与实现不符"** → 追加到 §5;
- **发现实现自身缺陷(bug)** → 追加到 §6(写明发现渠道:用户反馈 / reviewer / 测试),避免同一处反复返工;
- **推迟某项功能** → 不写在这里,写进 `docs/优化台账.md` 并编号 `OPT-xx`。
