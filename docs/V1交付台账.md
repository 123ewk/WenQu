## 1. V1 范围与"完整链路"的定义

**V1 = M1(账号与空间)+ M2(核心 RAG 闭环)后端全链路 + 前端 L0 对接。**

"完整链路跑通"指下面这条链路端到端可用(已由冒烟脚本实测,见 §3):

```
注册/登录 → 建空间(多租户隔离) → 建知识库 → 上传文档
  → [异步] 解析 → 分块 → 向量化 → 索引
  → 混合检索(向量 ∥ 全文,RRF 融合)
  → 流式问答(SSE)→ 答案带引用 → 引用可回溯到原文块
```

**V1 明确不包含**(不影响"链路完整"的判定,均属后续优化):
多副本。
(API Key 程序化接入、SSE 断线续流、父子分块、问答插件链化、Agent 工具调用(OPT-10)、
rerank 重排(OPT-27 按空间开关)原在此清单,均已交付。)
逐项来源、延后理由与触发条件见 **`docs/优化台账.md`**。

| 分块过散:一个小节被按段落切成多个碎块 | 用户反馈"chunk 太散" | 装块粒度取成了**段落**,而段落只是排版单位 | 改为**小节级装块**(不超上限即一块),超了按 段落→行→句→子句→字符 递归切;实测同一份简历 36 块 → 7 块(中位 375 token) |
| 分块面包屑出现同级标题、内容错位 | 用户上传真实简历 PDF 后肉眼发现 | PDF 解析把整页 span 拍平后**跨行**按字号相近合并,多行粘成一个"标题" | 以 pymupdf 的 line 为原子单位;逐行判定标题(长度 ≤40 字 + 不以句末标点/逗号结尾),连续同字号正文合并为段落 |

| 表格块被排到页尾 | 排查时实测 | 表格先于文字块产出,未参与排序 | 与文本行按 y 坐标统一排序 |
| 合并碎块后面包屑头重复 N 次 | 修复后复跑真实 PDF 发现 | `_merge_tiny` 直接拼 `content`,而 content 已含面包屑头 | `ChunkDraft` 保留 `body`,合并后 `render()` 重算 |
| 大字号长段落被判成标题而整段丢失 | reviewer 子代理审查 | 旧代码有 `len(text) <= 80` 兜底,重写时漏掉;chunking 不为标题产出块 | 恢复长度上限(40)并加句末标点判定;补测试 |
| `/ask` 显式选对话模型必 503 | 前端实测(缺口台账 §11.2-1) | 回答模型 id 被同时喂给检索向量化(要求 embedding 类型) | 检索向量改取目标 KB 的 `embedding_model`;请求 `model_id` 只驱动回答(SearchRequest.model_id 废弃保留) |

| `ChunkOut.tokens` 恒为 null | 前端实测(§11.2-4) | 入库流水线漏把分块 tokens 写进 chunk meta | tokens 随 meta 落库(存量文档 reparse 后有值);补单测 |
| `PATCH /spaces/{id}` 省略 `description` 会被清成空串,前端被迫把 name/description 一并提交防清空 | 前端对接文档 v2.2 §9.6 ⚠️ | `UpdateSpaceRequest.description` 默认 `""` 且服务层无条件赋值,违反 PATCH"省略=不改"语义 | 改为 `None`=不改动、显式 `""` 才清空(契约 description 变可选可空,重导);前端现有"整体提交"写法不受影响,后续可简化 |

## 7. 维护规则(交付侧)

- **模块增减或职责变化** → 更新 §2(以实际目录为准,不要照抄规划图);
- **每次大改动后重跑 §3 的命令**,用实测值覆盖旧值,勿手改估算值;
- **新增/下线契约端点** → 同步 §4 快照与 `docs/api/openapi.json`;
- **再次发现"文档与实现不符"** → 追加到 §5;
- **发现实现自身缺陷(bug)** → 追加到 §6(写明发现渠道:用户反馈 / reviewer / 测试),避免同一处反复返工;
- **推迟某项功能** → 不写在这里,写进 `docs/优化台账.md` 并编号 `OPT-xx`。
