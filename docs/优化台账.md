## 0. 编号与使用规则

- 编号规则:`OPT-xx`,连续编号,不回收已用编号。
- 每条必须写清:**来源/理由**、**为什么现在不做**、**什么条件下必须做**、**归属里程碑**。
- **未列入本表或 `docs/架构设计.md` §11 的工作,视为不在计划内** —— 不做"顺手优化"。

  一律进 §2 触发式或 §3 明确不做,不进里程碑内。

- OPT-29(上下文窗口使用率,2026-09-21,用户直接需求):"进度条显示本轮用了多少上下文"落地 ——
  `messages` 加 `context_used_tokens`/`context_window_tokens` 两列(迁移 0015,只写 assistant 行,
  user 行与老消息恒 NULL,**不回填历史**),两值同时进 SSE `done` 帧与 `MessageOut` → 刷新页面进度条可复原。
  **分子取"本轮最后一次上游 chat 调用"的 `prompt+completion`,不累加**(Agent 每轮重发同一份上下文,
  累加会报到超出窗口);**分母取那次调用实际解析到的模型的 `context_tokens`**,与模型身份一起在
  `UsageSink.bind()` 时记下,不另查目录。取值挂在 **OPT-28 的计量外壳**上而不是流水线里
  (`ChatTurnUsage` 收集器,`deps.get_chat_turn_usage()` 每请求一份、**刻意不 `lru_cache`**):
  Agent 的 prompt 由 `AgentRunner` 逐轮组装,流水线看不见,只有外壳看得见每一次真实上游调用;
  因此"调用没发生"守卫两边共用 —— 工具轮只吐 tool_calls 且厂商没回 usage 时既不落账也不进收集器。
  **null 三态即契约**:双 null = 本轮没打模型(兜底回答)或老消息;used 有值 + window null = 全局层

## 4. 维护规则(优化侧)

- **新增优化项** → 按 §0 的格式加进 §1 或 §2,写清来源、延后理由、触发条件、归属里程碑;
- **完成优化项** → 从本表移除,提交信息写明 `OPT-xx`,并在 `docs/V1交付台账.md` §2 补模块台账;
- **基准裁剪变化** → 同时更新 `docs/架构设计.md` §11(完整登记)与本表 §2(触发条件的通俗表述);
- **前端不受影响是硬约束** → 会改契约的项先确认前端 L0 已达标,否则推迟(见 §1.1)。
