## F1 = OPT-27 空间级模型配置

### 数据层(迁移 0013)

1. `model_providers` / `custom_models` 各加 `space_id UUID NULL FK→spaces ON DELETE CASCADE`;
   `NULL` = 全局层(superuser `/admin/*` 继续管,行为零回归);
   唯一约束调整:`model_providers.name` 从全局唯一改为 `(space_id, name)` 唯一
   (NULL 参与唯一性的 Postgres 语义用两条 partial index 分别钉住);
2. 新表 `space_model_settings`(空间模型总设置,一空间一行):
   `space_id` 主键、`embedding_key_encrypted`、`embedding_key_hint`、
   `rerank_enabled BOOL NOT NULL DEFAULT false`、`updated_by`、`updated_at`;
3. 内置 embedding 常量进代码(不放库):`EMBEDDING_PROVIDER_LABEL="阿里云百炼"`,
   `model_name="text-embedding-v3"`, `base_url="https://dashscope.aliyuncs.com/compatible-mode/v1"`,
   `protocol="openai_compatible"`, `dims=1024`, 官网链接 `https://bailian.console.aliyun.com/`。

### 解析链(改造 `ModelCatalog` / `model_client`)

- chat:`空间默认 chat → 全局默认 chat → 503 MODEL_NOT_CONFIGURED`;
  空间成员配了自己的模型就用空间的,运维全局兜底不变;
- embedding(**按环境区分,用户已裁决 2026-09-20**):
  空间 `space_model_settings.embedding_key` 存在 → 内置模型;
  不存在且 `settings.env == "dev"` → 回落全局层 embedding 配置(保住 dev/CI 存量链路);
  **`env == "prod"` 时不回落,直接 503 MODEL_NOT_CONFIGURED** —— 生产每空间必须自带 Key,
  配置页对"未配 Key"状态红警示;回落发生时日志打 WARNING(带 space_id),便于运维审计;
- rerank(新增):`rerank_enabled=true` 且空间有默认 rerank 模型 → 检索融合后重排;
  开关关 / 未配模型 → 跳过重排(现状行为);
- worker 入库:任务带 space 上下文,按上面的规则解析 embedding;失败进重试队列而非静默。

### 检索重排链路(现状:完全没有,本轮新建)

代码事实:现检索链路(混合融合 → 上下文组装)**不存在任何 rerank 阶段**,
`rerank` 此前只是模型 kind 的占位。本轮新增:

1. 协议注册表加 `cohere_rerank`(`POST {base_url}/rerank`,
   入参 `{model, query, documents, top_n}` → `results:[{index, relevance_score}]`,
   DashScope gte-rerank / Jina / SiliconFlow 等主流商均兼容此形态,base_url 用户自填);
2. 挂点:`retrieval.py` 融合产出 top-N(取 30)后、上下文组装前,对 query+文档调重排,
   按 `relevance_score` 重排取 top-K(沿用现有上下文条数预算);
3. **fail-open**:重排上游失败/超时(默认 5s 预算)→ 记 WARNING 并回落融合顺序,
   绝不因重排故障打断问答;
4. 未启用时零开销(不进协议调用)。

## F2 = OPT-28 空间 token 用量统计

> **已交付(2026-09-21)**。下面是实现后的口径,与计划的差异集中在三处:① 写入点做成
> **包装网关**而不是改调用点;② 未回填历史(用户裁决"从今往后计");③ token-usage
> **不登记进 API Key 能力表**(计划原写"归只读能力集",实现按人员数据 fail-closed)。

### 数据层(迁移 0014)

新表 `token_usage_events`:
`id, space_id, user_id, kind(chat|embedding), model_id TEXT, provider TEXT,
prompt_tokens, completion_tokens, total_tokens, source(upstream|estimated), created_at`。
明细行式存储(V1 体量下聚合查询直接走索引 `ix_usage_space_created` / `ix_usage_space_user`),
不预聚合;量大再上物化视图(触发式,不做)。

### 计量写入点

- **实现形态 = 包装而非改调用点**:`application/service/usage.py` 的 `UsageRecorder`
  包住 `ChatGateway` / `EmbeddingGateway`,在依赖注入层(`api/deps.py`)与 worker 装配。
  理由:Agent 模式一次提问打多次上游,**每次上游调用记一行**才不丢账;调用点散在
  问答/入库/探活多处,逐处插记账既漏又好错。
- chat:`_MeteredChat` 在流**关闭后**的 `finally` 记账,不破坏
  `chat_stream` 返回 Generator 的断连契约(`yield from` + 显式 `close()`);
  协议层经 `UsageSink` 出参带回上游 `usage`(openai_compatible 流式带
  `stream_options={"include_usage": true}`,仅在有 sink 时发;400/422 单发不带该字段重试一次);
  厂商不回 usage → `core/model_usage.estimate_usage_tokens()` 按
  **1 汉字 0.75 / 1 其他非空白字符 0.25、向上取整**估算并标 `source=estimated`。
- embedding:`user_id`=文档上传者(迁移后由 `ingestion` 的工厂第三参数传入),
  `space_id`=所属空间;取不到空间 = 无租户上下文,不记账(与 API 层网关同一口径)。
- 写入失败**不阻断**问答/入库主链路:记账整体 `except Exception → logger.warning`,
  用自己的会话写(旁路),集成测试把 session factory 弄坏仍断言 `done` 帧正常。
- **不计费**:重排与【测试连接】探活不走这两个网关,故意不记账(见对接说明 §2.5)。
- **两个估算器刻意并存**:`application/chunking.estimate_tokens()`(1 CJK 字 / 1 词 = 1 token)
  是分块预算用的粗略计数,`core/model_usage.estimate_usage_tokens()`(汉字 0.75、
  其他非空白字符 0.25、向上取整)是**对上游账单口径**的估算。两者用途不同,不要合并。

### 端点

| 方法/路径 | 门槛 | 返回 |
| --- | --- | --- |
| `GET /spaces/{sid}/token-usage?period=7d|30d|all` | Admin+(Role 30) | `{period,since,generated_at,space_total,members:[{user_id,username,nickname,role,prompt_tokens,completion_tokens,total_tokens,estimated_tokens,chat_calls,embedding_calls}]}` |

非成员 404(防枚举)、角色不足 403。`members[]` 按 `total_tokens` 降序、同值按用户名。
**Σ members ≤ space_total 是设计如此**:空间合计含 `user_id` 为空(上传者已注销)与
已退空间成员的明细行,花名册只列当前成员。

## F3 = OPT-29 上下文窗口使用率

> **已交付(2026-09-21)**。口径与计划有四处出入,都是实现时定下来的:
> ① 分子**不在组装点现算**,而是取"**本轮最后一次上游 chat 调用**"的 usage ——
> Agent 模式的 prompt 由 `AgentRunner` 逐轮组装,问答流水线看不见,只有 F2 的计量外壳看得见;
> ② 多轮**不累加**(每轮都在重发同一份上下文,累加会把用量报到超出窗口);
> ③ 模型 `context_tokens` 为空时**只让分母为 null**(分子照实给),前端走"窗口未配置",
> 与计划原写"两值均 null"不同 —— 双 null 专门留给"本轮没打模型/老消息";
> ④ 契约**不区分实测/估算**(前端 2026-09-21 裁决:进度条是仪表,≈ 口径只留在 F2 用量页)。

### 口径(实现后)

- `context_used_tokens` = 本轮**最后一次**上游 chat 调用的 `prompt_tokens + completion_tokens`;
  上游回传 usage 用实测,不回传才按 `core/model_usage.estimate_usage_tokens()` 估(与 F2 同一函数、同一守卫);
- `context_window_tokens` = **那一次调用实际解析到的**chat 模型的 `context_tokens`
  (随 `UsageSink.bind()` 一起记下,不是另查一遍目录);
- 三态:null/null = 本轮没打模型(兜底回答)或老消息;used 有值 + window null = 窗口未配置
  (全局层历史模型允许 `context_tokens` 为空);**used null + window 有值后端不得产出**;
- 一次上游调用都没发生(`ChatTurnUsage.sinks` 为空)→ `window()` 返回 None → 双 null;
- 断线宽限截止的 `partial=true` done 帧**同样带两值**,与完整回答同分支。

### 实现形态

- `core/model_usage.ChatTurnUsage`:一次问答内的 `UsageSink` 收集器,`window()` 取最后一次;
- `application/service/usage.py` 的 `_MeteredChat._settle()` 在**同一道"调用没发生"守卫**下
  把 sink 既喂记账也喂收集器 —— 厂商没回 usage 且该轮只吐 tool_calls 时两边都不落(与 F2 口径一致);
- `api/deps.get_chat_turn_usage()` 每请求一份,**刻意不加 `lru_cache`**(缓存它 = 跨请求串话 + 列表无界增长);
  FastAPI 缓存同请求内子依赖,所以网关与 `QAService` 拿到同一实例;

## 横切事项(每功能合并时执行)

- 契约:每功能合并后重导 openapi.json,基线路径/方法数在台账登记并同步前端文档;
- 授权表:每条新路由**显式决策**是否对 API Key 开放并登记进能力表。
  `/model-config/*`、`/token-usage*` 与 `/admin/*` 一样
  **刻意不登记** —— 端点只挂 JWT 依赖,带 Key 无 Bearer 实测 **401 `AUTH_REQUIRED`**(不是 403),
  不登记是第二道 fail-closed 防线。(原计划把 token-usage 归"只读能力集",实现时改判:
  逐成员用量是**人员数据**,机器凭证不该看到,故与配置页同等待遇。仓库里没有"只读能力集"
  这一独立概念 —— 能力表就是 API Key 可触达路由的白名单,不写即拒绝。)
- 加密铁律:任何 Key 不落明文、不回显明文、日志不出现;
- CI 无 .env:涉密钥/上游的新测试一律显式注入 dummy Key/打桩 transport(见台账既录教训);
- 风险预留:Anthropic 系协议未注册(名字清单可先含"协议=openai_compatible 的自建网关"路线),
  真接原生协议时按注册表加实现,不影响本三功能契约。
