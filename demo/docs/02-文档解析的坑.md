# 文档解析：入库质量的第一个瓶颈

很多人以为 RAG 效果差是模型不行，实际排查下来最先坏的是解析这一层。PDF 不是"文字的容器"，而是一种描述"某个坐标上画一个字"的版式格式，所以从 PDF 里读出来的文本顺序、分栏、页眉页脚都可能和人类理解的正文完全不同。

**四类典型脏数据**：

1. **双栏排版串行**。机器按坐标从上到下扫描，把左右两栏的一行行混在一起，读出来是一句人话都拼不出来的乱码。解法是先做版面分析，按列切区域再在区域内串行。
2. **页眉页脚和页码污染**。每页重复出现的公司名、章节名、页码会被切成大量重复块，检索时反复命中，属于噪声源头。一般用跨页重复行检测来剔除。
3. **表格线性化**。表格被展平成一堆单元格文字后，表头和行列关系全丢，"2025 年 Q3 营收"这类问题必然答错。工程上要么转成 Markdown 表格保留结构，要么转成"行首列：值"的键值句。
4. **扫描件与图片内文字**。这类页面根本没有文字层，只能靠 OCR（光学字符识别）加进去。OCR 的坑是错字率低但错的位置很要命——把专有名词、数字切错，检索就完全命不中。

**工程建议**：解析阶段一定要保留元数据——页码、章节标题层级、原文起止偏移。后面做引用溯源、父子分块回取原文、坏答案定位，全都依赖这些字段。只留一个纯文本字段的做法，等于把整条链路的可观测性砍掉了。

**成本视角**：解析属于一次性投入，可以慢慢跑、可以重试、可以人工兜底；而检索和生成是每次提问都要付钱的。把精力放在解析上，性价比远高于反复调生成端的提示词。
