# 分块策略与参数：为什么不能一把梭

分块（chunking）是把长文切成检索单位。它同时决定两件事：检索能不能命中，以及命中后喂给模型的上下文是否有用。这两个目标互相拉扯，所以不存在"最优块大小"，只有按场景取舍。

**三个必须理解的量**：

- **块大小**。太小（比如 128 个标记）语义不完整，一个概念被劈成两半，检索回来的片段读不懂；太大（2048 以上）单个块里混进多个主题，向量表示被稀释，而且占用宝贵的上下文预算。英伟达在其技术博客里公开过一组对比实验，测试了 128、256、512、1024、2048 标记五档，结论是事实型问答适合 256 到 512 标记的小块，金融类长文档可以放到 512 或 1024。
- **重叠（overlap）**。相邻块之间共享一小段文字，防止关键句正好落在切口上。同一组实验给出的推荐值是 15% 左右。重叠再大就是纯浪费——同一段文字被反复检索命中，融合排序时挤掉别的候选。
- **切法**。固定字数硬切最省事但最容易切坏；按段落/标题边界切语义完整；语义分块（检测相似度突变点再切）效果最好但要多算一轮嵌入，入库成本上去了。

**层级/父子分块**是实践里性价比很高的折中：用小块（子块）去检索，命中后回取它所属的大块（父块）喂给模型。这样检索精度和上下文完整性两头都占。代价是索引里要同时存两种粒度并维护父子关系，删除文档时要一起清理，否则会出现子块在、父块没了的悬挂引用。

**最实用的判断方法**：拿几十条真实提问做小规模评测集，只改分块参数，其他都不动，看命中率变化。凭感觉调参基本等于抛硬币。
