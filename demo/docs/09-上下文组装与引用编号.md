# 上下文组装：塞进模型的东西决定答案的质量

检索回来的片段不能直接拼给模型。上下文组装（context assembly）是把系统提示、历史对话、检索材料、当前问题按预算和顺序组织成一次请求的过程，它对最终效果的影响不亚于检索本身。

**顺序有讲究**。同一个模型对长输入的注意力分布并不均匀：开头和结尾的内容被读得更仔细，中间容易被忽略——这就是常说的"中间迷失"（lost in the middle）。所以最不该被忽略的东西要放在两端：指令放最前，当前问题和最关键的材料放最后。把最相关的片段塞进一堆材料中间，等于白检索。

**预算要显式管理**。模型有上下文窗口上限，超了要么报错要么被截断（截断位置不可控，通常丢的是最早的对话轮次，而那是用户设定要求的所在）。工程做法是：给系统提示、检索材料、历史对话各分配一段预算，按优先级依次裁剪，并在日志里记录每一段实际占用的标记数。没有这套预算，长对话的表现一定会随轮数衰减。

**历史不能只按条数截取**。多轮问答里，早期的结论性内容对后续问题影响很大。常见折中是"保留最近 N 轮原文 + 更早的历史压成摘要"。摘要要在生成前判断是否需要（用占用比例触发），别每轮都压。

**引用编号必须与材料顺序一致**。给每段材料标一个稳定编号，答案里的角标指向它。这里最常见的 bug 是重排之后编号跟着变了——检索时角标对得上、生成时指向另一段，用户一查就发现引用是假的。所以编号要在最终组装完成后按落地顺序重新分配，并且保存"答案—引用—片段"三者对应关系，事后复核才有依据。

**去重**。父子分块或多路召回很容易把内容重叠的片段同时塞进去，既浪费预算又让模型误以为"多处都这么说"从而提高置信度。组装前要按内容指纹或区间重叠度去重。
