# 前缀缓存：成本与延迟的最大杠杆之一

大模型按输入标记计费，而在 RAG 场景里输入往往远大于输出——一份检索材料加系统提示轻松几千上万个标记，答案只有几百。更浪费的是这些前缀内容在多轮对话里几乎原样重复发送。前缀缓存（prompt caching / context cache）就是为这件事设计的：服务端把请求前缀的计算结果缓存一段时间，下次前缀相同的请求直接复用，按缓存价格计费（通常是正常输入价的一小部分），首字延迟也明显下降。

**收益能有多大**：命中率高的稳定前缀，实测节省常在五到九成之间，具体取决于厂商计价和复用次数。对问答类系统，把系统提示、工具定义、长文档这类"每次都不变"的内容做成前缀，是投入产出比最高的成本优化。

**关键设计约束是"前缀必须逐字稳定"**。缓存按前缀匹配，一旦中间某个字节变了，后面的部分全部失效。所以：

- 把不变的内容放前面，易变的内容（当前问题、时间戳、随机 ID）一律放到最后。
- 系统提示里不要注入当前时间、请求 ID、随机排序的列表——这些会一次性打掉整段缓存。
- 检索材料的顺序要稳定（按固定键排序），别按分数浮点抖动排。
- 多轮对话里，历史前缀要连续追加，不要回头改写早期消息；一改写，那之后的缓存全丢。这也说明上下文压缩和缓存是有冲突的：压一次历史，缓存就断一次，所以压缩时机要少而准。

**观测要落到"这次请求命中了多少"**。厂商返回的用量字段里通常带缓存命中的标记数（不同厂商字段名不一样，有的嵌在明细对象里）。解析时要按"字段存在且为整数才算支持该能力"处理，命中 0 是正常情况而不是不支持；不支持时应当显示为"未知"，而不是显示 0% 误导判断。把这个数记进每次问答的用量里，才能算出真实节省，也才能在成本异常时发现前缀被打断了。
