# 重排序：把最相关的排到前面要多花一次模型调用

融合排序解决了"两路结果怎么合"，但它终究只看名次，不看内容本身。**重排序（rerank）**是另一类模型：把查询和候选段落成对喂进去，模型同时读两边，输出一个真正的相关度分数。这叫交叉编码器（cross-encoder），区别于嵌入模型那种"各自编码再算距离"的双塔结构。

交叉编码器明显更准，因为它能做词与词的细粒度对齐——同一段落在不同问题下的相关度会被给出不同分数。代价是贵且慢：每个候选都要跑一次完整前向，N 个候选就是 N 次。所以工程上绝不会对全部语料用它，而是**先用召回把候选缩到几十条，再重排这几十条**。

**候选窗口要设上限**。常见取 20 到 50 条重排。本项目取 30：再多收益递减，但延迟和费用线性上涨。一次重排请求塞进上百条候选，只会让问答的首字延迟明显变差。

**必须做的降级**：重排走的是外部模型服务，超时、限流、返回格式变化都可能发生。重排失败绝不能打断问答——拿不到分数就退回融合排序原样输出，并记一条警告日志。这条"失败开放"的策略很重要，因为重排只是锦上添花，检索链路本身已经可用。

**还有一个容易漏的细节**：上游有时会返回比请求数更少的结果（截断、内部过滤），也可能返回越界下标。代码要按"未覆盖的候选保持融合顺序补在尾部"处理，并丢弃越界项。假设上游一定返回全量、一定合法，就是线上故障的来源。

**什么时候不值得上重排**：语料同质、问题都是关键词式命中时，重排的收益很小；而问答型、需要判断"这段到底答不答得上这个问题"的场景收益明显。判断方法只有一个：拿固定评测集对比开与不开的指标差别。
