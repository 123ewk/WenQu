# 全文检索与中文切词：为什么还需要它

向量检索很强，但它有一类硬伤：**精确匹配**。产品型号、法条编号、人名、代码里的函数名，这些在语义空间里没有"相近"可言——搜 `ERR_1042` 时，向量会给你返回一堆"错误码相关"的段落，唯独不含它。所以生产级检索几乎都保留一条全文路，和向量路并行。

英文全文检索很成熟：BM25 算法配合词干化（stemming）和停用词表开箱即用。中文不一样，中文没有空格分词，必须先切词。常见的做法是在入库阶段用切词器（如 jieba）把正文切成词，拼成一个待索引字符串，再交给数据库的全文索引（Postgres 里就是 tsvector 那一列）。检索时用同样的切词器切问题，两边词形一致才能命中。

**这里有四个必踩的坑**：

1. **切词器必须两边同一个**。入库用 jieba、查询用另一套分词，词形对不上，全文路静默失效——最要命的是它不报错，只是永远返回不了结果，很晚才被发现。
2. **切词结果里混着标点**。切词器一般会把冒号、括号、问号原样吐出来。而全文查询语法里这些字符是操作符，直接拼进查询串会让整条语句报语法错误，把整个检索请求打挂。正确做法是把每个词当字面量处理（加引号并转义内部特殊字符），让数据库自己忽略无意义的词位。
3. **索引列要建对**。全文索引和向量索引是两种结构，各自要单独建；漏建索引时查询会退化成全表扫描，数据量一上来延迟就崩。
4. **排序分数不可比**。全文的相关度分数和向量的相似度分数分布完全不同，不能直接混在一起排序，必须走排名融合。

一句话总结：全文路不是向量路的备胎，它负责的是"必须一字不差"那一类查询，去掉它一定会在某个真实提问上翻车。
