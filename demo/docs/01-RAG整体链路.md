# 检索增强生成（RAG）的整体链路

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思想是：不把知识写进模型参数，而是在提问时临时把相关资料捞出来，塞进提示词让模型照着回答。它解决的是大模型两个固有缺陷——知识过时和不知道你的私有数据。

一条完整的 RAG 链路分两段，工程上必须当成两个独立系统看。

**离线段（入库）**：原始文档 → 解析（把 PDF/Word/扫描件还原成带结构的纯文本）→ 分块（切成适合检索的小段）→ 向量化（用嵌入模型把每块变成一串浮点数）→ 索引（写进向量库和全文索引）。这一段的特点是慢、可重跑、成本主要来自嵌入调用。

**在线段（问答）**：用户问题 → 同样做向量化和切词 → 多路召回（向量路 + 全文路）→ 融合排序 → 重排 → 拼进上下文 → 大模型生成 → 引用回指。这一段的特点是快、有超时预算、成本主要来自生成调用。

**最常见的误区**是把 RAG 当成"调个向量库"。真正决定效果的是解析质量和分块参数，模型反而排在后面。业界经验里，因为解析丢了表格结构或者分块把一句话切成两半而导致的坏答案，比因为模型能力不够而导致的更多。

**判断该不该用 RAG 的标准**：知识是否需要频繁更新、是否需要给出出处、语料规模是否超出上下文窗口。三问里有两个"是"就值得上 RAG；如果知识稳定且量小，直接写进提示词更省事也更准。
