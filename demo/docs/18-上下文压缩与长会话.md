# 上下文压缩：长会话为什么不越聊越笨

多轮会话越到后面越贵、越慢，而且质量下降。原因很直接：每轮都把之前所有对话原文重发给模型，历史轮数线性增长，输入标记数按平方级增长（第 N 轮要发前 N-1 轮的全部内容）。同时超长输入里"中间迷失"问题加剧，早期设定的要求被忽略。

**主流解法是滚动摘要压缩**：把最早的一批历史轮次交给模型总结成一段摘要，之后的请求只带"摘要 + 最近若干轮原文"。所谓滚动，是指随着会话变长反复做这件事，摘要本身也被不断合并更新。

**四条必须守住的工程约束**：

1. **触发条件按占用比例定，不按条数定**。不同问题长度差异极大，二十轮短问答可能只占窗口的 20%。常见做法是当"预估输入占上下文窗口的某个比例（如 80%）"时才压，留出安全边际给系统和检索材料。
2. **保留最近 N 轮原文不动**。近期轮次对指代理解至关重要，压掉就会出现"它指的是什么"的问题。N 通常取 4 到 8。
3. **摘要落库，原文不能删**。压缩改的是"下次请求带什么"，不是"数据库里存什么"。用户界面仍然能翻到完整历史，出问题也能回溯。只存摘要而丢原文的做法，等于为了省 token 毁掉了审计能力。
4. **要幂等、要能判断"没什么可压"**。已经压过的轮次不能被再压一遍，否则摘要会套娃式失真。对话太短时压缩反而丢信息，此时应当明确返回"未压缩"，而不是硬生成一段空洞摘要。

**摘要要点清单**。让模型只保留：用户明确提出的要求与约束、已达成的结论、正在追踪的问题、以及后续会引用到的事实。删掉寒暄和过程性描述。摘要长度要给上限，否则压完还是很长，等于白压一次调用。

**成本账要算清楚**。压缩本身要一次模型调用。如果会话马上结束、或者只再多问一轮，压缩是亏的。所以除手动触发之外，更省的做法是只在真正逼近窗口上限时同步触发一次。
