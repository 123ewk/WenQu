# 端到端评测与调参：怎么把改动变成结论

RAG 系统的参数有一大把：块大小、重叠率、召回窗口、融合权重、相似度阈值、重排候选数、上下文预算。凭感觉轮流调，最后谁也说不清哪个起了作用。正确做法是把每次改动变成一条可复现的结论。

**第一步：固定评测集**。五十到两百条真实提问，每条标注：期望命中的片段或文档、参考答案要点、以及"库里没有答案"这一类负样本。负样本必须有，否则你只能测出"答得多好"，测不出"会不会瞎答"。评测集一旦定下来就锁版本，不许边调边改题——那等于换了考卷还比较分数。

**第二步：分层归因**。同一批问题分别记录检索指标（召回率@K、MRR）和答案指标（要点覆盖率、忠实度、误答率）。两条曲线一起看才有结论：召回没上去就调检索侧（分块、权重、窗口），召回上去了答案还是错才去动上下文组装和提示词。

**第三步：单变量对照**。一次只改一个参数，其他全部固定，包括模型版本、随机性设置和重排开关。上游模型悄悄升级过一次，前后两天的数据就没有可比性——这是最容易犯的错，尤其是调用第三方服务时。

**第四步：留痕**。每次实验记下参数组合、评测集版本、各项指标、以及人工抽查的坏例子。没有留痕的调参等于没做，因为三个月后你只会记得"现在这套还行"，不记得为什么。

**几个反直觉的经验**：召回窗口的影响通常大于融合权重；分块参数改动会让历史结论全部作废，因为它换了检索单位本身；重排开启后收益的大小高度依赖语料同质程度，别人家的"必须上重排"不构成你的依据。

**评测要进流水线**。至少有一套冒烟级小评测集（二三十条）在改动后自动跑，避免大重构悄悄把检索打坏。全量评测定期或发版前跑一次。
