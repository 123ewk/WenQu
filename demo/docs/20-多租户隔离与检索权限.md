# 多租户隔离：把权限做进数据层而不是界面层

企业知识库天生是多租户场景：不同部门、不同项目的资料必须互不可见。这类系统最常见的事故不是被攻破，而是"某条查询忘了带租户条件"——一次遗漏就是一次跨租户泄漏，而且往往在数据量小的时候完全测不出来。

**可靠的隔离方式是让租户条件无处可藏**。具体三条做法：

1. **每一张业务表都有租户键，每一条查询都有租户谓词**。不要依赖"上层已经校验过了"，因为新加一条查询的开发者未必看得到那个上层。仓储层的方法签名里直接把租户键做成必填参数，忘了传就编译/类型检查阶段报错。
2. **越权访问返回"不存在"而不是"无权访问"**。403 会告诉探测者"这个 ID 确实存在，只是你不该看"，等于免费提供了枚举接口；统一返回 404 则让探测者无法区分"没有"和"不是你的"。这条对 ID 可预测的系统尤其重要。
3. **权限判定要覆盖检索路径，不只是接口层**。用户能调问答接口不代表他能拿到全库结果：问答前要把"这个人可访问哪些库"算出来，作为过滤条件带进检索 SQL。只在路由层鉴权、检索层查全库，是这类系统最典型的设计漏洞。

**共享与隔离的边界要显式建模**。有些内容确实要跨租户可见（公司制度、公共手册）。正确做法是给资源一个明确的共享属性，检索时条件写成"本租户的 或 标记为公共的"，而不是"某些租户偷偷不隔离"。后者迟早会变成谁都能看见。

**性能与隔离是同一件事**。租户键放进复合索引的首列，既保证查询只扫自己的数据，也避免大租户把小租户的查询拖慢。向量索引同理：在过滤后的小集合上做近邻搜索，比全库搜完再过滤既快又准——后一种做法会因为候选都被过滤掉了而出现"明明有相关内容却召回为空"。
