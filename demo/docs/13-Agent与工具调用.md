# Agent 与工具调用：让模型自己决定下一步查什么

普通 RAG 是固定流水线：检索一次、生成一次。Agent 模式的区别在于把"要不要检索、检索什么、够不够"这几个决策交给模型，形成一个循环——通常叫 ReAct（Reason + Act，推理与行动交替）：模型先想一步，然后发起一个工具调用，拿到观察结果，再决定下一步，直到它认为可以作答或触发终止条件。

**在知识库问答里它解决的是复合问题**。"对比 A 方案和 B 方案的适用条件"这类提问，一次检索很难同时捞全两边；拆成两次定向检索效果显著更好。同理，先查定义再查参数的手册类问题，也能靠多轮检索拼出完整上下文。

**工具接口设计有三条硬规矩**：

1. **参数用结构化模式描述**（JSON Schema），并给每个参数写清含义和取值范围。模型填错参数率和你描述的质量直接相关。
2. **返回值要可读且短**。把几千字的原始结果丢回去，会瞬间吃掉上下文预算，还会诱导模型继续误用。工具侧应先做摘要、截断和相关度过滤。
3. **失败要返回明确原因**。"没有结果"和"查询语法非法"要区分，否则模型会拿着空结果反复重试同一个错误姿势。

**循环必须有护栏，这是 Agent 最容易出事的地方**：

- **最大迭代次数**（常见 3 到 6 轮）和**总 token 预算**，两个都要设，超了就基于已有材料强制作答。
- **重复动作检测**：同工具同意图连续调两次以上说明模型在打转，直接终止。
- **人工确认门**：任何有副作用的动作（写数据、发消息、花钱）必须走确认，模型只能提议不能执行。

**成本要心里有数**。Agent 模式一次问答的调用次数是直检模式的数倍，延迟也从"一次生成"变成"多轮串行"。所以默认走直检、把 Agent 作为可选模式更划算。另外要意识到 Agent 路径依赖模型的工具调用能力，模型能力不够时它的表现可能明显低于固定流水线，这时评测集会直接告诉你该用哪种。
