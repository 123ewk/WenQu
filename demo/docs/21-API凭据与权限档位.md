# API 凭据与权限档位：机器调用怎么管权限

系统对外提供问答接口后，调用方不再只有"登录的人"，还有程序。程序用的凭据（API Key）和人的登录态是两套东西，混在一套权限模型里一定会出问题。

**凭据本身只该承担两件事：证明身份、指明归因**。把"能干什么"写在 Key 上是很自然的想法，但 Key 数量多、生命周期长，权限一改就要挨个改凭据，很快就会漂移。更稳的做法是把权限收进一个可复用的集合（叫它权限档位、角色或模板都行），凭据只引用这个集合。改档位就一次性影响所有引用它的凭据，而"这把 Key 是谁在用、什么时候创建的"这类归因信息留在 Key 上。

**范围收窄要能表达三档**：指定若干资源、全部资源、零资源。第三档容易被漏掉，但它是审计场景的刚需——"只留个记录，不给任何权限"。用空列表表达零权限会踩坑：很多代码把空列表当"未设置"从而回落到默认全部开放，这类 fail-open 是权限系统里最危险的一类 bug。正确做法是空与未设置用不同语义显式区分，默认一律 fail-closed。

**凭据的安全底线**：

- 只在创建时明文展示一次，服务端只存不可逆摘要，不存原文。丢了自己重建，谁也拿不回。
- 吊销不等于删除，但必须立即失效；长期不用的凭据要有清理策略。
- 日志、报错、审计记录里一律不落凭据原文，需要识别时用前缀片段（形如 `sk-abcd****`）代替。
- 凭据校验要走常量时间比较，且和登录态用不同的鉴权通道，避免一种凭据能冒充另一种。

**配额与归因要落到每次调用**。机器调用的量级波动远大于人，没有按凭据统计的用量记录，出问题既找不到源头也算不清账。用量记录还应包含失败与配额耗尽，否则"没数据"会被误读成"没需求"。
