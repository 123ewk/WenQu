# 跨会话事实记忆：让系统记住用户的偏好

会话内的上下文是模型自带的，关掉会话就没了。跨会话记忆是另一套东西：把"值得长期记住的事实"独立存下来，在下次任何会话里重新召回。对个人助理、企业内知识助手这类场景，它决定系统看起来是不是"认识你"。

**什么该记、什么不该记**。值得记的是稳定事实：用户角色、常用口径、偏好的输出格式、所在团队的规定。不该记的是本次任务的临时状态和一次性结论。判错会导致记忆库迅速膨胀并且相互冲突，最后召回的都是无用内容。工程上常见的约束是：单条记忆不超过一百多字、只陈述事实不复述对话、同类事实去重更新而不是追加。

**存哪里、怎么召回**。记忆条数很少（一个用户几十到几百条），但召回必须语义化，所以通常还是用向量：和文档分块用同一个嵌入模型，查询时按向量相关度取前几条注入上下文。这个设计的好处是能答出"用户以前说过偏好简洁表格"这种没有共同关键词的问题。成本是每条记忆要额外算一次嵌入。

**写入必须过确认门**。让模型自动往长期存储里写东西是危险操作：它可能记错、记进敏感内容，或者被文档里的注入指令诱导写入。更稳的做法是模型只提议，界面上给出"确认 / 编辑后确认 / 忽略"三个动作，用户点确认才落库。忽略也要留痕并带过期时间，否则模型会反复提议同一条，形成骚扰循环。

**归属边界最容易出错**。记忆属于"某个人"还是"某个空间里的某个人"，决定了谁能读到它。团队共享空间里，个人偏好被注入到同事的会话中是很常见的泄漏事故。正确做法是在存储层就带上归属键，读取路径强制按归属过滤，而不是在应用层判断。删除要连带召回索引一起清掉，只删主记录会留下"删了还能被检索到"的后遗症。
