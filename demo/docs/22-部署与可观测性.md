# 部署与可观测性：RAG 系统坏在哪要能立刻看出来

一套能跑的 RAG 系统由好几个差异很大的部件组成：Web 服务、后台入库任务、文档解析服务、数据库（含向量扩展）、对象存储、前端。它们故障模式完全不同，混在一起排查会非常痛苦。可观测性做得好不好，直接决定你是十分钟定位还是半天猜。

**部署形态**：单机容器编排（compose）足够支撑几十人内部使用，不必上编排平台。要点是：状态与计算分离（数据在卷里，容器随便换）、外部密钥只从环境变量注入且不进镜像、启动顺序有健康检查把关（数据库没就绪就别急着接流量）。

**部件要分别探活**。Web 服务活着不代表入库能跑：解析服务挂了，文档会永远停在"处理中"。所以每个部件都要有自己的健康端点，后台任务要有心跳和队列积压指标。"处理中的文档数超过阈值且长时间不降"这种告警，比"服务 503"更早暴露问题。

**日志要结构化，但绝不能带内容**。记录请求 ID、租户、耗时、各阶段标记数、命中的候选数、错误码，这些是排障需要的全部。文档正文、用户问题原文、凭据摘要都不该进日志——它们既是敏感数据又是体积炸弹。给日志加一层脱敏处理，比事后清理可靠得多，因为总会有新代码忘记这回事。

**错误要分类而不是分类文案**。用户看到的可以是一句友好提示，但内部必须有稳定错误码，区分"权限不足""资源不存在""上游超时""参数非法""配额用尽"。理由很实际：不同类别的处理方式完全不同——可重试的退避重试，不可重试的立即失败，越权的统一返回不存在。错误码同时要进接口契约并写成测试，避免哪天悄悄改掉让前端猜。

**数据库变更要走版本化迁移**。向量列、全文索引、租户字段这些结构变化，必须能在任意环境重复执行、且能回退。加一道"迁移头版本一致性"检查，能挡住绝大多数"本地能跑线上炸了"。
